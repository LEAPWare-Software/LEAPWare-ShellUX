## Findings

### F1: Fixed, for the scenario as described (CONFIRMED)

The change is in commit `b7343d2`, in `adapters/claude/repo_facts.py` (source and vendored copy both). A new function `_collect_proven_pr_numbers` reads each proof record's `"pr"` field and adds it to the set of known PRs:
```python
known = set(known_ids) | _collect_proven_pr_numbers(repo_root)
```

Reproduction: a scratch git repo with a landed commit titled "Some landed deliverable (#77)" and a proof record `feature-x.json` containing `"pr": 77`, run against both the vendored `collect_landed_unproven` and CI's own `lwb_check_proof.check_coverage`:
- At this PR's head: `S1_F1_branchnamed_pr77  hook_warns=False ci_fails=False AGREE`
- At the pre-fix commit `fe15e58`: `S1_F1_branchnamed_pr77  hook_warns=True  ci_fails=False DIVERGE`

Reverting the one-line fix (`known = set(known_ids)`) in both the source and vendored copy fails exactly one of the three new tests: `test_a_record_named_after_its_branch_but_declaring_the_pr_is_silent` (1 failed, 591 passed). A `"pr"` value of `"77"` (string) or `true` does not count — the field must be a real integer.

### N1: The fix's docstring claim of parity with CI is false, and one direction repeats F1 through a sibling field (CONFIRMED — the reason for DISAGREE)

The new docstrings say the hook now matches "the same two things `check_coverage` accepts: an id derived from the record's FILENAME … or a `"pr"` field" / "check_coverage matches by BOTH its filename-embedded id and any record's `"pr"` field". `scripts/lwb_check_proof.py::check_coverage` (lines 533-579) does neither: it accepts a typed `"pr"` field, or a `"commit"` field that is a prefix of the landed commit's SHA. It never looks at filenames. `commit` is one of the fields `proof/schema.json` requires, and CI's own error message recommends adding "a record naming its PR number **or commit**".

Side-by-side comparison at this head, same scratch-repo harness:
```
S0_no_record                       hook_warns=True  ci_fails=True  AGREE
S1_F1_branchnamed_pr77             hook_warns=False ci_fails=False AGREE
S2_backfill_commit_only            hook_warns=True  ci_fails=False DIVERGE
S3_filename77_no_pr                hook_warns=False ci_fails=True  DIVERGE
S4_filename77_pr12                 hook_warns=False ci_fails=True  DIVERGE
S5_nested_dir_pr77                 hook_warns=False ci_fails=True  DIVERGE
S6_pr_true                         hook_warns=True  ci_fails=True  AGREE
```

- **S2 is F1 again, through `commit` instead of `pr`.** A record added after merge whose `"commit"` names the landed SHA satisfies CI (following CI's own advice), but the hook still warns, because the hook reads `pr` and ignores `commit`.
- **S3/S4: the opposite direction.** A record named `proof/77.json` with no `"pr"` (schema allows this), or with `"pr": 12`, makes the hook treat PR #77 as covered while CI reports it unproven — silent when it should warn, the worse direction for a coverage check.
- **S5, newly introduced by this fix.** The new scan searches `proof/` subdirectories; CI only looks at the top level. Before the fix this case agreed (`True/True`); now it diverges.

Severity is moderate: both rules ship in `warn` mode, so nothing is blocked. But it is an unsupported equivalence claim, added in the very commit meant to fix a CI mismatch, and it is wrong in both directions — the pattern CLAUDE.md rule 2 and ADR-0001 Amendment G exist to catch. Smallest fix: either also accept a record whose `commit` is a prefix of the landed SHA (and drop or clearly label the filename match as an extension beyond CI), or narrow the docstrings to what is actually true; either way, add a test that runs the hook and `check_coverage` on the same fixtures and fails when they disagree.
