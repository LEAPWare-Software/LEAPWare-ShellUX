## Findings, most severe first

### CONFIRMED F1 (non-blocking, file as issue per rule 7). The regression test accepts a variant that would silently swallow every per-PR failure

`test_auto_queue_enqueue_step_does_not_abort_the_loop_on_first_failure` accepts `re.search(r"exit\s+\$\?", run)` as satisfying its "exits non-zero if any PR failed" assertion. It doesn't: after the loop, `$?` is the exit status of the loop's last `echo "::endgroup::"`, which is always 0 — so a hypothetical rewrite using `exit $?` instead of `exit "$rc"` would pass this test while always exiting 0, exactly the failure-swallowing shape B1 itself fixes. Reproduced with a probe script mutating the workflow and running both the real test suite and a literal `bash --noprofile --norc -eo pipefail` execution of each variant, PR list `1,2,3`, PR 1 stubbed to exit 1:

```
M0 shipped:        pytest -> 541 passed | bash exit=1, attempts=[1,2,3]
M1 revert B1:       pytest -> 1 failed (the new regression test) | bash exit=1, attempts=[1]
M2 `|| true`:        pytest -> 541 passed (test does not catch it) | bash exit=0, attempts=[1,2,3]
M3 `exit $?`:        pytest -> 541 passed (test does not catch it) | bash exit=0, attempts=[1,2,3]
M4 `|| echo ...`:     pytest -> 541 passed (test does not catch it) | bash exit=0, attempts=[1,2,3]
```
M2 was already named as a non-blocking gap by the embedded review; M3 is not, and is the sharper problem because the test's own regex explicitly allows it. The shipped `.github/workflows/auto-queue.yml` is correct — it uses `exit "$rc"`, not `exit $?` — so no PR#48 behavior is wrong today; the gap is only in what the test would catch if this line is ever touched again.

### PLAUSIBLE F2 (non-blocking, not reproduced, already disclosed in `proof/48.json`). A PR already in the merge queue may turn the step red on every 15-minute sweep

`main()` never checks whether a PR is already queued before calling `enqueue()` again. If GitHub's `enqueuePullRequest` rejects a re-enqueue of an already-queued PR, that maps to `EXIT_ERROR` → `rc=1` → the step goes red, indistinguishable in the job summary from a genuine failure (the loop's `::error::`-less `FAIL:` line does not name which PR failed without opening each `::group::`). The schedule sweep's concurrency group (`github.run_id`) never serialises against a `workflow_run`-triggered run's group (`head_sha`), so the two can race on the same PR. `proof/48.json`'s own `unproven` list already names this as "a known, accepted follow-up, not fixed here" — this finding does not add a new claim, it confirms the honest disclosure is accurate and not broader than stated. Not exercised against a live `enqueuePullRequest` call.
