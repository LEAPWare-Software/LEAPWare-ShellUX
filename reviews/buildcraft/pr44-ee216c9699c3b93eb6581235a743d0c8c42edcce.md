## Findings, most severe first

### 1. CONFIRMED locally, runner effect PLAUSIBLE: the "find PRs" step writes log lines into `$GITHUB_OUTPUT`, so the "lookup failure prints `prs=` and does not fail the job" contract is false

- **Where:** The workflow step is `run: python scripts/cloud/auto_queue.py --find-prs >> "$GITHUB_OUTPUT"`. That redirects all stdout, and the script prints its NOTICE lines to stdout in two places:
  - `emit_find_prs` (`print("NOTICE: could not resolve ...")`)
  - the existing `_api` helper (`print(f"NOTICE: gh api {path} exited {code}: {err.strip()[:200]}")`), which keeps any newlines inside gh's stderr.
- **Command** (`_run` stubbed to fail with a two-line stderr, no event file, so the schedule path runs):
  ```
  cd /tmp/lwb-pr44 && python3 -c "...a._run=lambda args:(1,'','HTTP 502 (x?y=1)\nsecond stderr line'); ... a.emit_find_prs()" > /tmp/lwb-probe-out.txt; cat -A /tmp/lwb-probe-out.txt
  ```
- **Output (the `emit_find_prs` part):**
  ```
  NOTICE: gh api repos/LEAPWare-Software/LEAPWare-BuildCraft/pulls?state=open&base=main&per_page=100 exited 1: HTTP 502 (x?y=1)$
  second stderr line$
  NOTICE: could not resolve pull requests for this event$
  prs=$
  ```
- **What goes wrong:** On any lookup failure, four lines land in the output file:
  - Two have no `=`. The Actions runner rejects such a line as an invalid output format and fails the step.
  - The first line does contain `=` (from `?state=open`), so it would register a junk output named `NOTICE: gh api repos/.../pulls?state`.
- **Effect:** The run goes red instead of printing `prs=` and exiting 0, which is what the `emit_find_prs` docstring and the PR body promise.
- **Why the test misses it:** `test_emit_find_prs_unresolved_prints_empty_prs_and_does_not_fail` stubs out `resolve_pr_numbers` entirely, so `_api`'s NOTICE never runs. It then asserts `"prs=" in out`, a substring check that would also pass on the output above.
- **Severity:** The failure is loud, not silent, so this is not a safety hole. It is a false tested claim in the one step the PR adds.
- **Regression:** The old heredoc printed only `prs=` lines.
- **Fix:** Send NOTICEs to `sys.stderr` in both `_api` and `emit_find_prs`. Assert that the whole stdout equals `prs=\n`.
- **Not reproduced:** this was not run in a real GitHub runner.

### 2. PLAUSIBLE: one failing PR in the sweep stops every PR after it, and nothing coordinates runs per PR

- **Loop behaviour:** The enqueue loop (`for pr in ...; do LWB_PR_NUMBER="$pr" python scripts/cloud/auto_queue.py; done`) runs under Actions' default `bash -e`.
  - Command: `bash -e -c 'for pr in 1 2 3; do echo "PR $pr"; if [ "$pr" = 1 ]; then false; fi; done; echo loop-finished'`
  - Output: `PR 1` then `shell exit=1`. PRs 2 and 3 never ran.
  - So any `EXIT_ERROR` from one PR ends that sweep for every PR listed after it: a ruleset read failure, an enqueue rejection, a head-sha race.
  - The loop itself is unchanged, but the new 15-minute sweep makes multi-PR iteration the normal case rather than a rare one.
- **No "already queued" check:** `main()` never checks whether a PR is already in the merge queue. Every sweep will call `enqueuePullRequest` again on each green PR that is still waiting in the queue.
- **No per-PR serialization:** The three triggers use different key spaces:
  - dispatch is keyed on the PR number
  - `workflow_run` is keyed on the head sha
  - `schedule` is keyed on `run_id`

  So the same PR can be evaluated and enqueued at the same moment by up to three runs.
- **What could not be settled:** whether GitHub treats a repeat `enqueuePullRequest` on an already-queued PR as a harmless no-op or as an error was not measured. If it is an error, finding 2 means red runs and starved PRs every 15 minutes.

### 3. Concurrency key walk-through: no collision between different PRs; the "old key evaluated empty" claim is correct

Key: `auto-queue-${{ github.event.inputs.pr_number || github.event.workflow_run.head_sha || github.run_id }}`

| Trigger | Key evaluates to |
|---|---|
| `workflow_dispatch` | `auto-queue-<pr number>` |
| `workflow_run` | `auto-queue-<40-hex sha>` |
| `schedule` | `auto-queue-<unique run id>` |

- **Different PRs never share a group.** Two `workflow_run` completions for different PRs have different shas.
- **Same sha shares a group.** CI and Handoff finishing on one sha share a group and are serialized, which is intended.
- **Pending runs get dropped.** With `cancel-in-progress: false`, GitHub still keeps only one pending run per group. A third run for the same sha (e.g. a re-run) cancels the older pending one. That is harmless, because only the latest evaluation matters.
- **Old key was empty.** The old expression had no `check_suite` or `inputs` for the new triggers, so it would have collapsed to `auto-queue-`. The PR's claim is correct.
- **What this means for the sweep:** Keying the sweep on `run_id` means it never serializes against the other triggers, which is the gap in finding 2.

### 4. CONFIRMED: `event.workflow_run.pull_requests` is never read

### 5. Security shape: holds (checked by reading the files, not by running a workflow)

- **Default-branch checkout:** The only checkout is `actions/checkout@v4` with `ref: ${{ github.event.repository.default_branch }}`. The workflow never fetches, checks out, or evaluates the PR head, and the `AUTO_TOKEN_QUEUE` steps run only default-branch `scripts/cloud/auto_queue.py`.
- **Schedule payload (unverified):** On `schedule`, `github.event.repository` may be absent from the payload. Even then, checkout falls back to `GITHUB_REF`, which is the default branch for schedule events. Safe either way.
- **Shell interpolation:** `${{ steps.find.outputs.prs }}` is inserted directly into a shell script. The values are now integers only; dispatch input goes through an `isdigit` check. That is stricter than the old heredoc, which echoed the raw dispatch input.
- **Workflow names match:** The declared names are `.github/workflows/ci.yml:1:name: CI` and `.github/workflows/handoff.yml:1:name: Handoff`, so the new `workflow_run` trigger is not vacuous.
- **Wrong-workflow completions:** `workflow_run.conclusion` and `.name` are never read. Readiness is always re-derived from the PR head's check-runs, so a completion of the wrong workflow cannot cause a premature "ready".
- **Unmeasured:** CI and Handoff also run on `merge_group` and on `push: main`, so their completions fire this workflow with queue-commit or main shas. What `commits/{sha}/pulls` returns for a `gh-readonly-queue` commit is untested; if it returns the queued PR, finding 2's re-enqueue applies.
