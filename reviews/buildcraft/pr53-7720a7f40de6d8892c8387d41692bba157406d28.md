## Summary

The re-cut itself is honest: none of #52's `bcee47f`, `df9ce2e`, `3056493` or
`ad92d5e` exist in this branch's history, every commit here has an
allow-listed author identity, and `lwb_check_commit_identity.py` passes.
The ported one-line `--first-parent` fix from #63 is byte-identical to
#63's own change. Full suite: 678 passed (not the PR's claimed 661 — that
number is stale, measured before this branch merged main; 609 base tests +
69 new = 678, verified).

But the new rule this PR ships (`lwb_no_unauthorised_destructive_action`,
build-plan 1.6) has two confirmed defects in its core allowlist mechanism
that neither of the two prior automated reviewers on this branch caught,
on top of the three non-blocking findings they did catch (which this
review independently reproduced and confirms still stand). Both new
defects mean the "authorised" check the PR's own description leans on —
"consuming repo's own policy explicitly allowlists it" — does not
actually hold for the two most obvious attack shapes against a
destructive-action guardrail: a chained command, and a multi-ref
push/delete. The rule ships at `warn` today so nothing is gated yet, but
the PR presents the allowlist as sound, and it is not; that gap is not
disclosed anywhere in the PR body or docs as a known limitation the way
this repo's own culture (see the three prior non-blocking findings, and
`reviews/README.md`'s own insistence on saying plainly what a check
cannot do) otherwise requires.

## Findings

### 1. CONFIRMED — an allowed command earlier in a chain hides an unallowed one later in the same chain

`_classify_command` returns only the first destructive command found in a
chain; `evaluate` then checks the allowlist against that one command only.
Reproduced directly:

```
policy: mode=DENY, options={"allow":{"history_rewrite":true}}
'git rebase main && git push --force origin main'  -> None   (should DENY)
'git push --force origin main && git rebase main'  -> Finding(DENY, 'a force-push')
```
The same two actions in the opposite order give opposite verdicts. This
is a real bypass of the rule's stated purpose once `deny` is armed: any
allowed action placed first in a chain silently authorizes everything
destructive after it. Not covered by any existing test — the one chain
test in the suite (`test_a_destructive_command_later_in_a_chain_is_still_recognized`)
has no allowlist in play.

### 2. CONFIRMED — a multi-ref command is judged on only one of its refs

```
'git push origin --delete a b'  -> ('delete_ref', 'b')   # only the LAST ref checked
'git push origin :a :b'         -> ('delete_ref', 'a')   # only the FIRST ref checked
policy: verified_landed_branches=["done"], mode=DENY
'git push origin --delete keepme done'  -> None   (keepme is deleted, unauthorized)
```

An unauthorized ref rides along with an authorized one and is never
evaluated — the two ref-list syntaxes also disagree with each other about
which ref even gets checked (last for `--delete`, first for colon
refspecs), which is itself evidence this path was never exercised against
more than one ref.

### 3. CONFIRMED (re-verified from the two prior AGREE reviews already on this branch, unchanged) — the ported `--first-parent` fix has zero test coverage on this branch

`grep -rn "first-parent" tests/` finds nothing added here; reverting the
ported line leaves all tests green on this branch (`80 passed` in
`tests/test_lwb_lanes.py` either way). The fix is real (verified: applying
#63's own test diff on top of this branch gives 81 passed with the port,
2 failed without it) but the coverage for it lives only on #63, not here.

### 4. CONFIRMED (re-verified, unchanged) — the rule is inert wherever repo facts aren't gathered, and `facts_incomplete` silences a verdict the rule could otherwise make correctly

`evaluate` reads `event.repo` only to go silent on `None`/`facts_incomplete`;
classification and the allowlist check never consult it. Reproduced:
`RepoFacts(facts_incomplete=True)` + `git push --force origin main` under
DENY -> `None`, even though nothing about the destructive-command
classification actually depended on the incomplete fact. Confirmed this
also means the rule never fires for the Codex adapter (gathers no repo
facts), as the docs already say.

### 5. CONFIRMED (re-verified, unchanged) — the classifier over-matches against its own documented under-match bias

```
'git rebase --abort'    -> ('history_rewrite', None)   # only restores pre-rebase state
'git rebase --continue' -> ('history_rewrite', None)
'git rebase --skip'     -> ('history_rewrite', None)
'git reset --hard'      -> ('history_rewrite', None)   # working-tree only, no history rewrite
```
Also found: `gh api -X POST repos/o/r/issues -f title=rulesets` misclassifies
as `settings_change` on an unquoted field value that happens to contain the
word "rulesets".

### 6. Minor, not previously flagged — additional under-match gaps

`git push origin +main` (force-push via `+` refspec), `git commit --amend -n`
(`-n` means `--no-verify` for commit, not dry-run, but is treated as
non-publishing), and `git -C x reset --hard HEAD~3` (`-C` only handled for
push) all classify as `(None, None)` — none flagged as destructive.

### 7. PLAUSIBLE, not fully reproduced — two `verifiable: false` exemptions may be over-broad

`proof/53.json` and `proof/53-lanes-first-parent.json` mark
`lwb_handoff.py --check` and `lwb_check_proof.py` as
`verifiable: false` / `nondeterministic-output`. The repo's own measured
table in `docs/maintainers/proof-of-completion-plan.md` lists both as
re-executable "yes", and other proof records in the repo mark the same
command `true`. `lwb_handoff.py --check` does print a byte count that
changes across commits, so the exemption is defensible at least for that
command — flagging the inconsistency with the repo's own table rather than
asserting it is wrong.

## What holds

- The re-cut's central claim (carries only `ad92d5e`'s content, excludes
  the bad-identity commit and its dependents) is CONFIRMED.
- The `_allowed` mechanism itself (`options["allow"][category] is True`,
  strict; `verified_landed_branches` for `delete_ref`) matches the PR's
  description of it, for the single-command, single-ref case.
- Merge commits are unconditionally exempted, which is correct and
  intentional, not a gap.
- The shipped default (`warn`, empty `options`) means none of the above
  currently gates anything in production.
