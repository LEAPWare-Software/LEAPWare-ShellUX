## BLOCKING

### B1. [CONFIRMED] Command injection: a `workflow_dispatch` input reaches a `run:` shell block under `pull-requests: write`
`.github/workflows/auto-queue.yml`'s "find" step prints the raw `pr_number` input into `$GITHUB_OUTPUT` unsanitised:
```python
manual = (event.get("inputs") or {}).get("pr_number")
if manual:
    print(f"prs={manual}")
```
The next step interpolates that output **directly into the `run:` body text**, not via `env:`:
```yaml
run: |
  for pr in $(echo "${{ steps.find.outputs.prs }}" | tr ',' ' '); do
```
GitHub substitutes `${{ }}` before bash parses the file, so this is code, not data. Reproduced with the exact loop body, substituting the expression for `1"; touch /tmp/pwned.txt; echo "`:
```
::group::PR #1
(would enqueue 1)
::endgroup::
--- side effect? ---
-rw-r--r-- 1 root root 0 Sep 19 14:59 /tmp/pwned.txt
```
The job log reads as an ordinary single-PR run while an arbitrary command executes — this is the "guard passes while what it guards is broken" shape, in a merge-enforcement workflow, and it directly contradicts the file's own stated design ("a PR must never be able to edit the job that decides whether it may merge"): that principle is applied to the checkout ref but not to this input. `workflow_dispatch` requires repo write today, so this is not a cross-privilege escalation for the common case, but it is a real injection sitting beside a write token, and per this codebase's own rules a defect this reachable is not deferrable. Fix: `env: PRS: ${{ steps.find.outputs.prs }}` and reference `"$PRS"` inside the shell body.

### B2. [CONFIRMED] The module's stated safety property about the merge queue is false as written
`scripts/cloud/auto_queue.py`'s docstring: *"The merge queue then re-runs every required check before merging, so this job cannot land anything the ruleset would refuse -- it can only ask."*
Read from the live ruleset (unauthenticated GET, read-only):
```
$ curl -sS https://api.github.com/repos/LEAPWare-Software/LEAPWare-BuildCraft/rules/branches/main
... 9 required contexts: test (ubuntu/windows/macos-latest, 3.10/3.12) x6, lwb-portable (ubuntu/windows/macos-latest) x3
```
`lwb-lanes`, `lwb-proof-pr` and `lwb-commit-identity` are **steps inside the `test` job**, each gated `if: always() && github.event_name == 'pull_request'`. In a `merge_group` run (what the queue actually triggers) those steps are skipped, but `test (...)` still reports success — so the review gate, the proof gate and the identity gate are inert exactly where the docstring claims re-verification happens. Combined with the live ruleset's `required_approving_review_count: 0`, the enqueue decision itself is the last point the independent-review gate is evaluated, not the queue. Scope is bounded — `enqueue()` pins `expectedHeadOid` to the sha whose `pull_request` run did execute these gates — but the claim as written overstates what the queue re-verifies and must be corrected or narrowed, not left as a stated safety property backed by no test.
