### CONFIRMED — F3: two of `resolve_pr_numbers`'s stated guarantees are not pinned where they are actually wired in

The one test that exercises this path (`test_resolve_pr_numbers_from_workflow_run_uses_head_sha_not_pull_requests`) seeds `"pull_requests": []`, so "ignored the field" and "read an empty field" look identical to it. `proof/44.json` acceptance criterion AC4 ("never trusts event.workflow_run.pull_requests") is recorded `met: True` on the strength of a test that cannot actually distinguish trusting from not trusting a non-empty value of that field.

The escalation-bug fix this guards against is tested at the `resolve_pr_numbers` level (mutating that function's own `if event_name == "schedule"` line does fail a test), but the wiring that actually feeds it the real event name at the CLI entry point is not.

### CONFIRMED — F7: the enqueue loop can be starved by one erroring PR, more consequential now that the schedule trigger runs a full sweep

The Enqueue step has no `shell:`, so it runs under `bash -e`; a PR read failure, ruleset read failure, or enqueue rejection all exit 1 and stop the loop. Reproduced in a stand-in 3-PR loop: the first PR's non-zero exit stops the other two from being processed at all in that run. Before this PR the loop typically had at most one PR to consider (from a single `check_suite`); the new 15-minute sweep makes multi-PR lists the normal case, so one bad PR now silently blocks every PR queued after it in the same run — not confirmed against real GitHub enqueue-rejection behavior (e.g., re-enqueuing an already-queued PR), flagged as unconfirmed rather than a live finding.

### CONFIRMED — the `concurrency.group` rekey claim holds, and is untested

The old expression evaluated to the same empty group for both new triggers; the new `inputs.pr_number || workflow_run.head_sha || github.run_id` gives each scheduled run its own group, while CI and Handoff finishing on the same sha correctly share one. No test covers this (mutation M11, removing the `run_id` fallback, leaves the suite unchanged at 535 passed) — informational, not a blocker on its own, but relevant to F7: a scheduled run and a `workflow_run`-triggered run for the same PR are not serialized against each other.
