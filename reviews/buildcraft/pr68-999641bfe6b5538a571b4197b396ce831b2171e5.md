## Findings

### F1 — CONFIRMED, blocking for the stated contract: a pull request is accepted as "the linked issue"

`scripts/lwb_check_acceptance_criteria.py` (~line 601) fetches `GET /repos/{o}/{r}/issues/{n}` and reads only `created_at`. It never inspects the response's `pull_request` key, which is exactly the field that distinguishes an issue from a PR in that endpoint's response shape. Reproduced against real GitHub data, using PR #68's own commit range (first commit `2b83009e`, authored 2026-09-25T12:33:40Z):

```
"Closes #67" (real issue)        -> PASS: issue #67 created 2026-09-25T12:18:27Z ...   exit=0
"Fixes #1"   (real PR, not issue)-> PASS: issue #1 created 2026-09-17T20:53:35Z, 7 days 15:40:05 earlier -> "PASS"  exit=0
"Fixes #60"  (real PR, not issue)-> PASS: issue #60 created 2026-09-24T23:45:22Z, 12:48:18 earlier -> "PASS"       exit=0
"Fixes #68"  (itself, a PR)      -> FAIL: postdates the first commit by 0:00:35                                    exit=1
```

Of this repo's 69 numbers, only 4 (#33, #36, #59, #67) are issues; the other 65 are PRs, almost all older than any given deliverable's first commit — so an arbitrary small `#N` will very likely PASS regardless of whether it names real acceptance criteria. This directly contradicts the module docstring's "Only a linked GitHub issue counts" and issue #67's own criterion 2 ("naming the issue that states this deliverable's acceptance criteria").

*Why BuildCraft's own reviewer missed it:* its test double (`_fake_gh`) answers every issue-id lookup with `{"created_at": ...}` only — no PR-shaped payload is ever exercised — and its one live run used PR #68's own body, which happens to name a real issue (#67).

### F2 — CONFIRMED, and wider than previously reported: the non-GitHub side of the comparison is author-controlled, undisclosed

The script anchors one side of the comparison on GitHub's `created_at` (real, external) but the other side on `git log -1 --format=%aI <sha>` — the commit's *author* date, which the author sets. The module docstring claims "every evidence source we control can be forged... The evidence is external by construction" without disclosing that only one operand is actually external. Reproduced in a scratch repo, checked against the real `created_at` of issue #67 (2026-09-25T12:18:27Z):

```
[honest]     author=committer=2026-09-20T10:00Z              -> FAIL                              exit=1
[future2030] author=2030-01-01T00:00Z, committer=2026-09-20Z -> PASS                               exit=0
[plausible]  author=committer=2026-09-25T12:20:00Z            -> PASS (0:01:33 after issue created) exit=0
[honest commit + `git commit --amend --no-edit --reset-author`] -> PASS (2:38:12 after)             exit=0
```

The last two cases show that rejecting a future author date, or an author date later than the committer date, would **not** close this — `--reset-author` alone produces an author date that is neither future nor later than the committer date, yet is fully attacker-chosen. This is partly inherited from the underlying design (issue #67 criterion 3 itself specifies comparing against the first commit's author date), so the defect specific to this PR is the undisclosed limitation, not necessarily the wrong design choice — but as shipped, the HONEST SCOPE section overclaims "external by construction."

*Why BuildCraft's own reviewer missed it:* its mutation probes only alter existing code paths, so they cannot surface a check that was never written; its one relevant test frames the question as "author date vs. committer date," never "both are author-controlled."

### F3 — CONFIRMED (BuildCraft's own reviewer's N1, independently re-verified): `load_exemptions`'s file-level validation is untested

Six mutations at the file level (invalid JSON → treated as zero exemptions; non-list top level accepted; non-dict entry silently skipped; the `pr`/`branch` type checks removed; unreadable file → zero exemptions) all leave the 27-test suite green. "Invalid JSON silently becomes zero exemptions" is the repo's own named defect shape — "checked and found nothing" indistinguishable from "could not check" — and the docstring's claim that this "never" happens is unguarded.

### F4 — CONFIRMED as further test gaps of the same shape (code itself currently correct)

Each of the following guards can be individually removed with all 27 tests still green: the check for a missing `created_at` field; the naive-timezone guard; the empty-range guard (removing it would raise `IndexError` rather than reporting `NO_RANGE`); the base==head guard; `_gh_api_json`'s handling of malformed JSON or a non-object JSON value. (The trailing-`Z` rewrite mutant also survives, but is a known equivalent mutant on Python 3.11 where `fromisoformat` accepts `Z` natively — not re-tested on 3.10.)

### F5 — CONFIRMED, low severity: a malformed exemption file can exit under the wrong code

`load_exemptions` catches `OSError` but not `UnicodeDecodeError`; a non-UTF-8 `acceptance_exempt.json` raises uncaught, producing exit 1 (`ACCEPTANCE_EXIT_FAIL`) rather than the documented exit 4 (`CONFIG_ERROR`). The failure is loud (a traceback), just misclassified.

### F6 — PLAUSIBLE, minor: a git-resolution failure is reported under the wrong stated cause

When `_run_git` returns `None` (e.g. `--repo-path` points at a nonexistent directory), the message says `--base does not resolve` regardless of which side actually failed to resolve. Outcome classification (`NO_RANGE`) is still correct; only the named cause can mislead.
