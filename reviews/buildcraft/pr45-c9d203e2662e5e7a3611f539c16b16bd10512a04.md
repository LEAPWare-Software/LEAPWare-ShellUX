## Findings

### F1 (CONFIRMED, blocking): an id with no real session token now escapes the self-review check

`_parse_identity` still accepts a stoplisted product name (e.g. "buildcraft") sitting in the session-token slot. `_id_segments` then discards that segment before the two ids are compared for a shared long segment. On `main` (before this PR's stoplist existed), the same pair of ids was correctly flagged as colliding.

Command and output:
```
reviewer-cloud-routine-buildcraft-2026-09-24 | author-claude-buildcraft-2026-09-24
  parsed: ('reviewer-cloud-routine', 'buildcraft', '2026-09-24') ('author-claude', 'buildcraft', '2026-09-24') errs: []
  shared: None
reviewer-claude-LeapWare-2026-09-24 | author-claude-leapware-2026-09-24
  parsed: (..., 'LeapWare', ...) (..., 'leapware', ...) errs: []
  shared: None
MAIN shared: buildcraft
```
- Failure scenario: a reviewer dispatch that forgets to append its real session token produces an id whose token segment is literally "buildcraft" (this repo's own routine-mandated reviewer prefix is `reviewer-cloud-routine[-b]-buildcraft-`, per the two records actually filed in `reviews/45/`). If the commit author's id makes the same mistake, `_review_ok` now treats the pair as independent instead of flagging the collision `main` would have caught. "There was no token to compare" and "I compared and found no shared token" collapse into the same accepted outcome.
- Fix suggested: have `_parse_identity` reject a session-token segment whose `.lower()` is itself in `IGNORED_ID_SEGMENTS`, with a regression test.

### F2 (CONFIRMED, test gap): three wiring mutants survive the new tests

Full tree copied to a scratch dir (no `.git`) and `tests/test_lwb_lanes.py` + `tests/test_lwb_check_commit_identity.py` run against each mutation. Baseline: `81 passed`.
```
== no-trailing-slash: 81 passed      (reviews_prefix = f"reviews/{pr_number}", no trailing "/")
```

- `no-trailing-slash`: nothing catches a prefix collision between PR numbers (e.g. `reviews/450/` or `reviews/45x/` would wrongly count as record-only for #45 under this mutation). The shipped code has the trailing slash and is correct; the protection just isn't pinned by a test.
- `head-walk-pr0` and `cli-drops-flag`: the shipped wiring is correct (verified directly, see below) but untested — a future edit could silently drop the `--pr-number` plumbing without failing CI.

### F3 (CONFIRMED, framing correction): relative to `main` (not #40), the identity gate gains a new exemption rather than only narrowing one

`git show origin/main:scripts/lwb_check_commit_identity.py | grep -c record_only` → `0`. The broad record-only exemption in `_authors()` only ever existed on #40's branch — it is not present on `main`. So against `main`, this PR both (a) adds a brand-new, correctly-scoped identity exemption for `reviews/45/**` and `proof/45.json`, and (b) makes the reviewable-head walk in `lwb_lanes.py` stricter than before. The PR body's framing ("used to treat ANY commit... as exempt") is only true of #40, not of `main`.

Separately, reviewers don't write proof records, yet `proof/<pr>.json` is exempted from the identity check with no stated reason — once exempt, any git identity can write or edit the PR's proof record without it moving the reviewable head or failing identity.

### F4 (PLAUSIBLE, not newly introduced): proof record can be edited post-review without going stale

Because `proof/<pr>.json` commits are skipped by the reviewable-head walk, `proof/45.json` could be edited after an AGREE record lands without invalidating it. `main` already has this weakness over the whole `proof/` directory; this PR narrows the blast radius (from all of `proof/` to one file) but does not close it. Not reproduced.

`scripts/lwb_lanes.py:708` still tells users "record-only commits under reviews/ and proof/ are excluded" — should read `reviews/<pr>/` and `proof/<pr>.json`.
