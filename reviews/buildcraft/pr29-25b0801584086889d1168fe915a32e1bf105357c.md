## Findings

### Finding 1 — CONFIRMED, blocking. The new merge-critical gate accepts a review record that names no commit at all

`scripts/lwb_auto_queue.py:197,206`:
```python
reviewed = str(record.get("reviewed_commit", ""))
...
if not head.startswith(reviewed):
```
`head.startswith("")` is `True` in Python, so a record with `reviewed_commit` missing, blank, or a single character is treated as reviewing the current head. Driving the real `review_records` with a stubbed `_gh`:
```
reviewed_commit MISSING entirely             -> good=1 problems=[]  ACCEPTED_BY_AUTO_QUEUE=True
reviewed_commit = '' (blank)                 -> good=1 problems=[]  ACCEPTED_BY_AUTO_QUEUE=True
reviewed_commit = '2' (1 char)                -> good=1 problems=[]  ACCEPTED_BY_AUTO_QUEUE=True
reviewed_commit = 'deadbeef' (wrong, 8 char) -> good=0 problems=['reviews/29/evil.json: reviewed_commit deadbeef is not this head']  ACCEPTED_BY_AUTO_QUEUE=False
```
The last row is the control proving the check isn't simply inert. The canonical gate (`lwb_lanes._review_ok`) refuses all three bad cases:
```
reviewed_commit MISSING entirely  -> accepted=False errors=["reviews/29/zz_probe.json: missing required field 'reviewed_commit' (reviews/schema.json)"]
reviewed_commit = '' (blank)      -> accepted=False errors=["... 'reviewed_commit' = '' does not match pattern '^[0-9a-f]{7,40}$' (reviews/schema.json)"]
reviewed_commit = '2' (1 char)    -> accepted=False errors=["... 'reviewed_commit' = '2' does not match pattern '^[0-9a-f]{7,40}$' (reviews/schema.json)"]
```
The divergence is wider than this one field: `review_records` runs no schema validation at all, never checks the record's `pr` field against the directory it was found under, and never requires `reviewer_was_dispatched_by_author`. Records with `reviewer_id: "a"` / `commit_author_id: "b"` (which `lwb_lanes._parse_identity` rejects outright for PR ≥ 19) were also accepted by `review_records`.

Failure scenario: with `LWB_AUTO_QUEUE=armed`, any `reviews/<pr>/*.json` containing `{"verdict":"AGREE","reviewer_id":"a","commit_author_id":"b"}` — no commit named, no schema conformance, no parseable identity — satisfies readiness and the PR is enqueued for merge. Fix mirrors the canonical gate: `if not isinstance(reviewed, str) or len(reviewed) < 7 or not head.startswith(reviewed):`, plus a regression test.

### Finding 2 — CONFIRMED, blocking. The checkout guard asserts `ref` *exists*, not what it says

`tests/test_lwb_auto_queue.py:411`:
```python
unpinned = [s for s in steps if not (s.get("with") or {}).get("ref")]
```
Truthiness only. Adding a `pull_request:` trigger to the real workflow with the checkout pinned to the PR's own head — the canonical dangerous shape:
```yaml
  pull_request:
    branches: [main]
...
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.pull_request.head.sha }}
```
```
$ python3 -m pytest tests/test_lwb_auto_queue.py -q

$ python3 -m pytest tests/ -q

```
Nothing in the repository catches this. That is PR-controlled code executing under the workflow-level `permissions: pull-requests: write` (`.github/workflows/lwb-auto-queue.yml:38-40`).

In fairness: the danger is latent, not live, at this head — the workflow's only triggers are `workflow_dispatch` and `push: branches: ['cloud/**']` (no `pull_request`/`pull_request_target`/`workflow_run`), and the guard is not entirely vacuous: with the trigger added and the checkout left *unpinned*, it does fire (`1 failed, 26 passed`, `test_the_workflow_never_checks_out_pull_request_code_under_a_write_token` fails as expected). So the guard catches the naive mistake and misses the realistic one — value-blind, which is the exact failure mode it claims to fix.

### Finding 4 — CONFIRMED, medium, not charged by BuildCraft's own embedded reviewer. Command injection in the workflow's `run:` line

`.github/workflows/lwb-auto-queue.yml:84` interpolates a `workflow_dispatch` input directly into a shell line, in a job holding `pull-requests: write` with `GH_TOKEN` in the environment:
```yaml
run: python scripts/lwb_auto_queue.py --pr "${{ github.event.inputs.pr }}"
```
GitHub substitutes textually before the shell runs, so `argparse`'s `type=int` offers no protection — the shell has already split the line by the time argparse sees it. Input `1"; echo INJECTED-ARBITRARY-COMMAND-RAN; echo "` rendered and executed the injected `echo`. Exploitation requires dispatch (write) access, so this is hardening rather than a privilege-boundary break, but it is new merge-critical code and the fix is free: pass the input through `env:` and reference `"$PR"` in the script instead of interpolating into `run:`.
