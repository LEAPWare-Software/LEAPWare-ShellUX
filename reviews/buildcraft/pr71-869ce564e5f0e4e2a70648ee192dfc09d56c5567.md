### 1. Non-blocking, but real: the proof record's evidence commands were copied from #70 and pinned to a commit they never ran against

File: `proof/lwb-recut-70-stale-disagree.json`. Its `commands[]` array is
identical to #70's proof record; only the `commit` field was changed
(`diff <(git show pr70:proof/lwb-item-1.8-hook-matcher-name.json | jq
commands,commit) <(git show pr71:proof/lwb-recut-70-stale-disagree.json |
jq commands,commit)` shows only `< e4a14ceeb47d...` vs `> ffc4bbe03c97...`).
The `lwb_check_commit_identity.py` entry's `resolved_head` is
`e4a14ceeb47d7d0d5f4114beae89c89ef87b8353` — `git branch -a --contains
e4a14ce` returns only `pr70` and `remotes/origin/lwb-item-1.8-hook-matcher-name`;
that commit is not in #71's history at all. The record's own `commit`
field (`ffc4bbe`) is not what any of its listed commands were actually run
against. The record also still marks "Full test suite green with no test
changes needed, since this is docs-only" as `met: true`, which stopped
being true once this PR started changing `tests/test_lwb_lanes.py` and
`scripts/lwb_lanes.py`.
Why the gate doesn't catch it: `scripts/lwb_check_proof.py:360-372` only
checks that `resolved_head` looks like a SHA-shaped string; it never
cross-checks it against the record's own `commit` field or the PR's actual
history — a field read while its sibling that would falsify it is never
consulted. `lwb_check_proof.py --pr 71 --base 0d1be71 --head 869ce56` still
prints `lwb-proof check passed (24 record(s))`, exit 0. This is an
accuracy defect in the evidence file's provenance, already reachable via
this same gap on `main` before this PR — nothing in this PR's own code
introduces it, and today nothing downstream actually breaks because of it.

### 2. Non-blocking, pre-existing on main: a record-only deletion of a DISAGREE clears the gate with no link back to what was deleted

`independent_reviews` (scripts/lwb_lanes.py:914-915) globs whatever
currently exists under `reviews/<pr>/*.json` at the head; a commit that
only deletes a file under `reviews/` is record-only and skipped by the
first-parent walk. Reproduced in a throwaway detached worktree of #70,
removed after: before deleting, `lwb_lanes.py --base <mb> --head HEAD
--pr-number 70` printed `FAIL: reviews/70/cloud-reviewer-b.json: verdict
is 'DISAGREE', want 'AGREE'`, exit 1. After `git rm
reviews/70/cloud-reviewer-b.json` + commit: `lwb-lanes check passed`, exit
0. Nothing in the mechanism links a re-cut PR to its parent's dissent
either — a new PR number starts with an empty `reviews/<n>/`, so a still-
valid objection is dropped by default unless a fresh reviewer happens to
re-check it. In this specific PR the objection WAS re-checked: reviewer B
reproduced the original DISAGREE's substance under a fresh record, and
this review independently re-verified the underlying claim (docs fix is
real, see "Claims checked" below) rather than taking the record's
existence on faith. This is the exact class of defect BuildCraft's own
reviewer brief asks to hunt for ("a stale objection silently outvoted by
staleness, by design" — except here the design gap is that staleness
protection has no memory of a deleted record, not that it outvotes one).
It is pre-existing on `main`, not introduced by this PR's diff.
