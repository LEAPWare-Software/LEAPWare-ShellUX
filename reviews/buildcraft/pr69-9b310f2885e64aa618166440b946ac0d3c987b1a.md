## Summary

The code does what the PR claims: `is_bot_pr_author` correctly matches only a trailing `[bot]` suffix, case-insensitively, and correctly rejects non-bot logins including ones that merely contain "bot"; the exemption is scoped to only the self-record check inside `check_pr_has_record` (every other gate — lanes, commit identity, env-leak, post-merge coverage — is untouched by this PR and unaffected); and the CLI path always prints the exemption as a `NOTICE:`, never silently. Real regressions were not found. The test suite as written is weaker than the PR's coverage claims: mutation testing found three survivors, one of which removes the anchor the code's own comment calls load-bearing. None of the three is a correctness defect in the shipped code today — they are coverage gaps against a correct implementation.

## Findings

### Confirmed correct — the bot-login match

`is_bot_pr_author` is `re.compile(r"\[bot\]$", re.IGNORECASE)`, applied only to `str` input:

```
None -> False | '' -> False | '[bot]' -> True | 'DEPENDABOT[BOT]' -> True | 'dependabot[bot]' -> True
'not-a-bot]' -> False | '[bot]-fake' -> False | 'robot-wrangler' -> False | 'botulism' -> False
'foo [bot]' -> True | 'foo[bot] ' -> False | 'foo[Bot]' -> True | 123 -> False
```

One non-exploitable edge case: `$` in Python regex also matches immediately before a trailing `\n`, so `'foo[bot]\n'` matches. A GitHub login cannot contain a newline, so this cannot be triggered through the real CI wiring — informational only.

### Confirmed correct — the exemption's scope

The early `return []` in `check_pr_has_record` skips only that function's own record lookup. Verified other checks still run and still fail a bot PR that has an unrelated problem:

```
$ python3 scripts/lwb_check_proof.py --pr 99999 --pr-author "dependabot[bot]"
NOTICE: pr-authority: PR #99999 author 'dependabot[bot]' is a recognized bot account -- exempted ...
FAIL: proof/69.json: is new in this PR but self-declares 'pr' (69) instead of 99999 ...
exit=1
```
A correctly-scoped record with a bot author passes cleanly (`lwb-proof check passed`); a non-bot author on the same PR still fails exactly as before. The lane, commit-identity and env-leak gates live in other scripts this PR does not touch.

### Confirmed — the notice is non-silent via the CLI, with one caveat

`main()` always passes `notices=` and prints every entry as `NOTICE: ...`. Calling `check_pr_has_record` directly with `notices=None` (its default) skips the notice with no error — the docstring says "if given", so this is documented behavior, not a bug, and `main()` is the only production caller today.

### Plausible, not exploitable through GitHub — who can obtain the exemption

`--pr-author` is wired from `github.event.pull_request.user.login`, which the PR opener cannot set directly. Ordinary GitHub usernames cannot end in `[bot]` (reserved for GitHub App accounts), so a human cannot self-grant this exemption by choosing a username. Two points worth the author/reviewer's attention rather than a defect: (1) any installed GitHub App gets the exemption, not just Dependabot — currently only `dependabot[bot]` appears in this repo's PR history, so this is latent rather than active; (2) an AI-agent App (e.g. a hypothetical `claude[bot]`) capable of writing its own proof record would still be exempted from having to. Neither was independently verified against GitHub's account-naming rules; this is stated from general knowledge, not measured.

### Confirmed gap — mutation testing shows three untested branches, one on the PR's stated load-bearing anchor

Each of these leaves `tests/test_lwb_check_proof.py` fully green:
```
drop the trailing `$` anchor from the bot regex     -> 38 passed  (SURVIVES)
drop re.IGNORECASE                                  -> 38 passed  (SURVIVES)
remove main()'s --pr-author wiring entirely         -> 38 passed  (SURVIVES)
```
Contrast with mutations that ARE caught: matching plain "bot" as substring (1 failed), removing the NOTICE (1 failed), exempting unconditionally (5 failed). The missing coverage: no test exercises a login with `[bot]` not at the end (e.g. `[bot]-fake`), no test exercises mixed case, and — most concerning — no test runs `main()` with `--pr-author` at all, so the actual CI wiring that is supposed to turn Dependabot PRs #60/#61 green has no regression test protecting it.

### Confirmed — no vendor rebuild owed

`git diff --name-only` against `core/`/`adapters/` paths is empty; `python3 scripts/lwb_build.py --check` reports both vendor trees match source.

### Test run

`python3 -m pytest tests/test_lwb_check_proof.py -k bot -q` → 4 passed, 34 deselected. `python3 -m pytest tests/ -q` → 615 passed on a clean run; one run hit `tests/test_lwb_lanes.py::test_is_record_only_commit_true_for_a_merge_with_empty_first_parent_diff` failing intermittently (this PR touches neither `lwb_lanes.py` nor its tests — consistent with the pre-existing flake already tracked against open PR #63, per other reviewers' records on this repo).

### CI wiring

The login is interpolated directly into the `run:` block (`--pr-author "${{ github.event.pull_request.user.login }}"`) rather than via `env:`. Not exploitable — GitHub logins cannot contain shell metacharacters — but the neighboring established convention in this file for a genuinely free-text value (PR branch names, per PR #68's F1/F5) is to use `env:` specifically to avoid relying on that argument. A style nit, not a defect, since a login's character set is fixed by GitHub.
