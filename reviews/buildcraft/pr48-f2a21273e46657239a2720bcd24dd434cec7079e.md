## Findings, most severe first

### CONFIRMED F1 (non-blocking, file before merge per rule 7). The B1 regression test passes against loop rewrites that reintroduce the bug or silently swallow every failure
The test only checks two surface properties of the step's `run:` text: every `auto_queue.py` invocation line contains `||`, and `exit "$rc"` or `exit $?` appears somewhere in the text. It does not check what the `||` assigns, whether `rc` is ever reset, or whether the `exit` actually runs after the loop completes. Six loop-body mutations, each run first against `pytest tests/test_workflows_parse.py`, then reproduced under `bash --noprofile --norc -eo pipefail` with a stub PR loop (101, 102, 103; the "FAIL=" line shows which PR was set to fail and what was actually attempted):

```
M0 (original pre-fix 3-line loop, the actual regression case): pytest FAILS (1 failed, 7 passed) — correct baseline
M1 (`|| true` in place of `|| rc=1`, keeping `exit "$rc"`): pytest 8 passed (should fail — this silently reports success on every PR failure)
   FAIL=101: exit=0 attempted=[101,102,103]   FAIL=102: exit=0 attempted=[101,102,103]
M2 (`|| true`, `exit $?` instead of `exit "$rc"`): pytest 8 passed (same silent-success defect, also accepted)
M3 (`exit "$rc"` moved inside the loop body): pytest 8 passed (should fail — this reintroduces PR-starvation)
   FAIL=101: exit=1 attempted=[101] only        FAIL=102: exit=0 attempted=[101] only (102, 103 never reached)
M4 (`rc=0` re-executed inside the loop each iteration): pytest 8 passed (should fail — resets an earlier failure)
M5 (`|| rc == 0` typo for `|| rc=1`): pytest 8 passed (should fail — never actually sets rc)
```
M3 is the worst case: it passes the test, attempts only the first PR (the exact original bug), and can report success (`exit=0`) even though a later PR would have failed, because the premature `exit` never reaches the failing iteration. M1/M2 are the change most likely to actually get written later, since "the queue check keeps failing, let's swallow the error" is a natural, wrong fix a future editor could make and the test would wave through. A faithful test would extract and execute the real `run:` text under `bash -eo pipefail` with a stub PR loop, the way this review did above — a few milliseconds of cost. This does not mean the shipped code is wrong; it is. It means the regression guard protecting it is materially weaker than the PR body's "confirmed non-vacuous" claim, since that mutation testing exercised exactly one mutation (the literal revert), not the space of plausible future edits.

### PLAUSIBLE F2 (non-blocking, operational). An already-queued PR may turn this step red every 15 minutes for as long as it sits in the queue
`scripts/cloud/auto_queue.py`'s `main()` has no check for "already queued" — a queued PR is still `open`, still has green checks, and still targets `main`, so the schedule sweep calls `enqueuePullRequest` on it again every tick. If GitHub's GraphQL mutation rejects a duplicate enqueue with a nonzero `gh` exit (not verified live from this review — no GraphQL access), `enqueue()` returns `False`, `main()` returns `EXIT_ERROR`, and with this PR's own fix the step now carries that failure through to a nonzero exit every single tick until the PR merges or leaves the queue. The PR's own `proof/48.json` records the already-queued case as a known, deliberately-unimplemented gap, which is honest — but the interaction with F1 (a test that would not catch a `|| true` workaround) is not recorded anywhere, and a recurring, expected red X is exactly the kind of signal that gets "fixed" by suppressing the error rather than filtering the cause.

### CONFIRMED F3 (low). Per-PR failures get no `::error::` annotation naming the failing PR
Each PR's processing is wrapped in `::group::PR #$pr`, and `auto_queue.py`'s own `FAIL: ...` lines land inside that group on stdout, so the failing PR is findable by expanding the log — but neither the loop nor the script emits a `::error::` line, so GitHub's own annotations/run summary show only the step's overall `exit 1`, with no PR number surfaced there.

### PLAUSIBLE F6 (low, carried over from #47, not new in this PR's delta). Minor input-handling gaps in `resolve_pr_numbers`
