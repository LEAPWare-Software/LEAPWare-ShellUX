**3. An unreadable/malformed event file silently turns a targeted run into a full sweep of every open PR.**
```
NOTICE: could not read GITHUB_EVENT_PATH: Expecting ',' delimiter: line 2 column 1 (char 36)

NOTICE: could not read GITHUB_EVENT_PATH: [Errno 2] No such file or directory: '.../nope.json'

```
`emit_find_prs` replaces an unreadable event file with `{}`, and `resolve_pr_numbers({})` reads that as "no event data" → falls through to the schedule-sweep path. This is the exact "could not check" vs. "found nothing" conflation the review brief asks to hunt for. Blast radius is limited because `main()` re-checks every required check live before enqueueing anything, but a malformed `workflow_run`/`workflow_dispatch` payload silently becomes a repo-wide sweep instead of failing loudly.

**4. Diagnostic NOTICE lines are written to stdout, which is redirected straight into `$GITHUB_OUTPUT`.**
The step is `python scripts/cloud/auto_queue.py --find-prs >> "$GITHUB_OUTPUT"`. A failed API call produces:
```
NOTICE: gh api repos/.../commits/abc/pulls exited 1: HTTP 502
NOTICE: could not resolve pull requests for this event
prs=
```
Two of those three lines are not `key=value` and are almost certainly rejected by the Actions runner's output-file parser (reasoned, not reproduced against a real runner — see PLAUSIBLE 7).

**5. New: in the multi-PR schedule sweep, one PR erroring stops every PR after it in that run.**
`EXIT_ERROR = 1`; the loop step has no explicit `shell:`, so GitHub Actions runs it under `bash -eo pipefail`, which aborts on first nonzero exit:
```
$ bash --noprofile --norc -eo pipefail -c 'for pr in 1 2 3; do echo "PR #$pr"; [ $pr != 1 ]; done; echo reached-end'
PR #1
step exit=1
```
Failure scenario: the schedule sweep lists PRs [A, B, C]; if A's enqueue call is rejected or its PR read fails, B and C are silently never considered in that run, and (if A's error persists) never on the schedule path at all — the exact path meant to be the self-heal/retry for a `workflow_run` that never fires. None of the three prior review records caught this; it is only reachable now that the schedule trigger can hand the loop more than one PR.

**6. The trigger/workflow wiring itself is untested.**
`grep` across `tests/` and `scripts/` for `auto-queue.yml` / `workflow_run` finds only `tests/test_auto_queue.py` and `auto_queue.py` itself — nothing reads the actual YAML. Every new test calls `resolve_pr_numbers`/`emit_find_prs` directly, so the `on:` block, the concurrency key expression, and the find-step wiring are unobservable to the suite.
