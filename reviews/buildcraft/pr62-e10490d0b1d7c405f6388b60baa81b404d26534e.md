## Summary

The gate arms correctly and is not vacuous: mutation-probing the structural
guard fails named tests in both `scripts/lwb_check_proof.py` and
`scripts/lwb_record.py`, and the four-way `--reexecute` exit contract
(0/1/2/3) is real, distinct, and correctly prioritized (mismatch beats
uncomparable). The `proof/39.json` reclassification is an honest fix, not
a hidden escape hatch: `lwb_handoff.py --check` really does print a byte
count that changes on every merge, reproduced directly by diffing the
digest across three commits. The real CI run for this head (Windows
3.10/3.12 leg log read directly) shows the gate armed and passing for the
right reason, not a false pass. One claim in a later reviewer's own commit
message overstates what the mechanism protects against; the PR's own body
does not make that overstatement and already discloses the actual gap.

## Findings

### Confirmed — the structural guard is not vacuous

Mutation-probed both modules in scratch copies, restored after each:
gutting `STATE_DEPENDENT_COMMAND_NEEDLES` in the validator
(`scripts/lwb_check_proof.py`) fails exactly 3 named tests
(`test_handoff_check_marked_verifiable_true_is_rejected`,
`test_handoff_check_module_form_marked_verifiable_true_is_also_rejected`,
`test_check_state_claims_marked_verifiable_true_is_rejected`); gutting the
recorder's copy (`scripts/lwb_record.py`) fails 2 named tests
(`test_run_command_rejects_verifiable_true_for_lwb_handoff_check`,
`test_run_command_rejects_verifiable_true_for_lwb_check_state_claims`).
The tip commit's own review record claims "1" test fails for the recorder
case — this is CONFIRMED WRONG, it is 2. Not a defect in the shipped code;
an inaccuracy in an intermediate reviewer's commit message, worth
correcting in that record but not blocking.

### Confirmed — the four-way `--reexecute` exit contract is real

0 (all matched, reproduced on this head), 1 (mismatch — forced a wrong
digest on a `verifiable: true` command, got `MISMATCH: 1`, exit 1), 2
(nothing re-executed — forced every record's commands to `verifiable:
false`, got the `NOTHING WAS RE-EXECUTED, THIS PROVES NOTHING` line, exit
2), 3 (uncomparable — changed a record's `sanitiser_version`, got
`UNCOMPARABLE … THIS IS NOT A PASS`, exit 3). Mismatch correctly takes
priority over uncomparable in `reexecute_exit_code`.

### Confirmed — the "nothing re-executed" protection is set-wide, not per-record, and the PR's own body already discloses exactly this

Added one new synthetic record with every command marked `verifiable:
false` and fabricated hashes: the overall run still reported `33 of 172 …
ALL RE-EXECUTED COMMANDS MATCHED`, exit 0 — the new all-exempt record
contributes only a `0 of 5` line under an otherwise-green summary, it does
not trip exit 2. This matches — does not contradict — the PR body's own
honesty-gap disclosure: "An author can still mark every command in a
record `verifiable: false` with a plausible reason, re-execute nothing,
and get a green, now-blocking gate for a record that opted out of
verification entirely." The PR is correct that this is visible in the
printed per-record line, not prevented. A later reviewer's commit message
states "a record set exempting every command fails the job rather than
going green" without qualifying that this is true only of the *entire*
set of records repo-wide, never a single new one — that line should be
read as describing the exit-2 case in general, not as a claim that one
bad record is individually caught. Worth tightening that wording in a
follow-up; does not change the verdict on this PR, since the PR's own
text never makes the stronger claim.

### Confirmed — the `proof/39.json` reclassification is honest, with one imprecise description carried into the code comments

`python3 scripts/lwb_handoff.py --check`'s printed byte count is of the
**whole** `HANDOFF.md` file, not only its generated block as the PR body,
code comments and `proof/39.json`'s new note say — verified by reading
`cmd_check` directly. The substance of the claim (the count is
merge-dependent and cannot reproduce) still holds: measured byte counts of
2942 / 2960 / 2956 across three different commits, with differing re-run
digests. The captured evidence fields (argv, exit, tail, sha256,
sanitiser_version) are unchanged by the reclassification commit, as
claimed.

### Plausible, disclosed by design — a wording change to any of the 7 covered scripts' success messages will break this gate

Changing `lwb-prefix check passed` to add a trailing period reproduced
`MISMATCH: 12 command(s) did not match`, exit 1, across old records. This
is a property of re-executing old records against a live gate generally,
not introduced by this PR, but it means future routine text changes to
these scripts now carry a merge-blocking cost that didn't exist before
this PR armed the gate. Worth the owner knowing, not a reason to withhold
this PR.

### Plausible, not reproduced — the name-specific check can likely be evaded by splitting the target name across argv tokens

E.g. invoking `lwb_handoff.py` indirectly via a constructed string rather
than a literal argv token containing the name. Reasoned through, not
executed. This is consistent with the PR's own framing of the guard as
name-specific rather than a general state-dependent-output detector — a
guardrail against the repeated accidental mistake, not an integrity
control against deliberate evasion, and CLAUDE.md's own vocabulary
distinction (integrity control / entry-point validation / guardrail)
applies here: this is a guardrail, and nothing in the PR claims otherwise.

### Confirmed, from the real CI run — the gate is armed correctly on this head, not just locally

Read the actual `test (windows-latest, 3.12)` job log for this PR's head
(run on merge commit `991bc32`) directly: `617 passed`, then `TOTAL: 33 of
167 commands re-executed, 0 uncomparable, 19 skipped-self, across 24
records -- ALL RE-EXECUTED COMMANDS MATCHED`. All six `test` legs report
`success` on the check-runs API for this head; only one leg's full log was
read, the other five are inferred from job conclusion rather than log
content.
