## 1. BLOCKER — the timeout defect is unfixed in the other gate that launches the hook, and the commit says otherwise

`scripts/lwb_check_hook_launch.py` — the check backing the `lwb-portable` CI job, matrixed
over windows/macos/ubuntu — still launches the shipped hook as a subprocess with a
hardcoded `timeout=30`:

```
scripts/lwb_check_hook_launch.py:59   def _hook_command(hooks_json: Path) -> str:
scripts/lwb_check_hook_launch.py:62       if entry.get("matcher") == "Agent":
scripts/lwb_check_hook_launch.py:64               return hook["command"]
scripts/lwb_check_hook_launch.py:90               timeout=30,
```

This is the same shape as BLOCKER 1, in the same repository, in the sibling script: it
reads `command` out of the hook dict *to avoid assuming*, then ignores the sibling
`timeout` key (10, in both `plugins/claude/lwb/hooks/hooks.json` and
`plugins/codex/lwb/hooks/hooks.json`) that decides whether the command ever completes.

The commit message states: *"VERIFIED BY ME: the hook subprocess now runs at the declared
timeout while the two remaining timeout=30 calls are git invocations."* The two remaining
`timeout=30` calls **in the edited file** are git invocations. There is a third, in
`lwb_check_hook_launch.py`, and it is not a git invocation — it is the hook subprocess.

Reproduced, same probe as the commit used (`time.sleep(12)` at the top of
`plugins/claude/lwb/bin/lwb_hook.py:main`, declared timeout 10):

```
$ time python3 scripts/lwb_check_hook_launch.py
lwb-portable check passed
real	0m12.132s
EXIT=0

$ time python3 scripts/lwb_check_foreign_repo.py
FAIL: hook exceeded its declared timeout of 10s (plugins/claude/lwb/hooks/hooks.json) for
command 'python3 ".../plugins/claude/lwb/bin/lwb_hook.py" || python ".../lwb_hook.py"' --
Claude Code would kill this hook at that timeout in a real session, so lwb_proof_required
would never get to run
real	0m10.137s
EXIT=1
```

Removing the `timeout` key from the Bash entry entirely reproduces the same asymmetry — one
gate refuses to run, the other does not notice:

```
$ python3 scripts/lwb_check_foreign_repo.py
FAIL: the Bash PreToolUse entry in .../hooks.json declares no numeric 'timeout' -- this
check refuses to substitute a value hooks.json does not itself declare ...
EXIT=1
$ python3 scripts/lwb_check_hook_launch.py
lwb-portable check passed
EXIT=0
```

Why this is a blocker and not a nit:

- The `lwb-portable` step is named, in `.github/workflows/ci.yml:221`, **"Run both hooks
  exactly as each hooks.json declares them."** The declared timeout is part of what
  hooks.json declares, and it is the part this job ignores. The step name is the claim; the
  code does not meet it.
- `lwb_check_foreign_repo.py` covers the **Bash** matcher only. `lwb_check_hook_launch.py`
  is the only check in the repository that ever launches the **Agent** matcher entry — the
  matcher `lwb_version` ships under, and the one `proof/27.json` already records as never
  having been observed to fire. So for the Agent entry, the declared 10s is enforced
  nowhere, on any OS, and a 10–30s Agent hook still passes CI green while being killed in
  every real session. That is precisely the consequence the commit message calls "worse
  than a gate bug".
- It is also the only check that touches the **Codex** plugin's hooks.json, so the Codex
  side gets no declared-timeout enforcement at all.

Two smaller sibling-key defects in the same function, found by the sweep the brief asked
for:

- `_hook_command` ignores `commandWindows`. `plugins/codex/lwb/hooks/hooks.json` declares
  `"commandWindows": "python \"${PLUGIN_ROOT}\\bin\\lwb_hook.py\""`, and
  `scripts/lwb_validate_codex_plugin.py:74` treats that key as real. The `lwb-portable`
  matrix includes `windows-latest`, and on that leg it launches `command`, not the string
  the host would actually use. The one OS where the sibling key changes the meaning is the
  one OS where the check does not read it.
- `entry.get("matcher") == "Agent"` is exact string equality, where the sibling script
  documents and implements `"|"`-splitting (`lwb_check_foreign_repo.py:88-92`). A matcher
  of `"Agent|Task"`, or Claude Code's wildcard form, makes this check `SystemExit` with
  "no PreToolUse/Agent hook found" rather than exercise the hook. That failure is loud, so
  it is ranked low — but the two scripts should not disagree about how a matcher is read.

Fix that would clear this finding: read the whole entry in `_hook_command` (as
`_bash_hook_entry` now does), require a numeric `timeout`, pass it to `subprocess.run`, and
launch `commandWindows` on Windows when the manifest declares one.

## 3. BLOCKER — the same conflation, two lines from the fix: `Policy.degraded` is computed and discarded

`core/lwb_core/config.py` computes a reason for every degraded policy, and its module
docstring says so explicitly: *"if the policy dict is missing, malformed, or missing a
rule's config entirely, that rule's mode resolves to 'off' **and the condition is recorded
so an adapter can log it**."*

No adapter logs it. `degraded` / `degraded_reason` are read by no hook, no adapter, no
script:

```
$ grep -rn "degraded" --include=*.py . | grep -v /vendor/
core/lwb_core/config.py:58,59,78,82,85...      (set here)
tests/core/test_config_fail_open.py:9,15,26,34 (asserted here)
...and nowhere else in adapters/, plugins/*/bin/, or scripts/ except unrelated prose
```

`bin/lwb_hook.py` now surfaces `policy_error` (the file could not be *read*) on the line
above, and drops `policy.degraded` (the file read fine and is structurally broken) on the
line below. Measured against the shipped hook, four policy files, one event
(`git push -u origin HEAD`, branch `feat-x`, record present):

```
=== {"rules": []}  (parses; degraded_reason="policy has no 'rules' object") ===
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"}}

=== {"rules": {"lwb_proof_required": {"mode": "denied"}}}  (typo'd mode) ===
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"}}

=== {"rules": {"lwb_prof_required": {"mode": "deny"}}}  (typo'd rule id) ===
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"}}

=== not json at all  (the one path this commit fixed) ===
{"hookSpecificOutput": {..., "permissionDecision": "allow", "permissionDecisionReason":
"lwb: policy unreadable at /tmp/unreadable-policy.json (JSONDecodeError: ...) -- falling
back to a policy with every rule off"}}
```

The first three are `{"permissionDecision":"allow"}` **with no reason at all** — the exact
string the commit message quotes as the defect it removed. A policy whose JSON is valid but
whose shape or spelling is wrong is far more likely in a consuming repo than a policy file
that cannot be parsed, and `RuleMode.coerce` does not even set `degraded` for an
unrecognised mode string, so a one-character typo silently disarms an armed rule with no
trace in the output and no trace in the ledger.

Fix: append `policy.degraded_reason` to the same `extra_warnings` list, and have
`RuleMode.coerce` report an unrecognised mode rather than only returning OFF.

## 4. BLOCKER — the repo-facts path that was patched barely occurs; the ones that occur are still conflated

`adapters/claude/repo_facts.py`'s own contract is *"Fail-quiet: every failure here returns
None or an empty result **rather than raising**"*. The commit wraps `collect_repo_facts` in
`try/except Exception` — that is, it catches the case the module is written never to
produce — while the failures it does produce still return the same values as "checked,
found nothing".

Measured against the shipped hook. Scratch repo `/tmp/probe_repo`, branch `feat-x`,
`proof/feat-x.json` present, hook run as an unprivileged user:

```
A. proof/ readable (record present), default policy
   -> allow, reason: "lwb 0.1.0: reporting only, no policy enforced yet"

B. chmod 000 proof/ (the SAME record still on disk), default policy
   -> allow, reason: "... ; publishing command with no proof record for 'feat-x':
      0 record(s) found under proof/ or .lwb/proof/, none matching."

C. chmod 000 proof/, policy {"lwb_proof_required": {"mode": "deny"}}
   -> {"permissionDecision": "deny", "permissionDecisionReason": "publishing command with
      no proof record for 'feat-x': 0 record(s) found under proof/ or .lwb/proof/, none
      matching. ..."}

D. chmod 000 .git/HEAD, record deleted (a REAL violation), deny mode
   -> {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "allow"}}

E. same as D with .git/HEAD readable (control)
   -> deny, as expected
```

No `lwb: repo facts unavailable` marker appears in any of them, because nothing raised:
`collect_proof_ids` swallows the `OSError` with `continue` and returns `()`, and
`read_branch` returns `None` — the same `None` it returns for a detached HEAD, as its own
docstring admits (*"None for a detached HEAD ... and for any read failure"*).

Consequences, in the repository's own terms:

- **C is a false deny.** The gate blocks a publish and states as fact that it counted the
  records and found none, when it could not read the directory. A gate that denies on
  evidence it did not have is the failure mode `lwb_proof_required`'s "UNDER-match,
  deliberately" posture exists to avoid, and it is worse than the warn-side misses that
  posture accepts.
- **D is the silent allow this PR claims to have eliminated**, byte for byte
  (`{"permissionDecision":"allow"}`, no reason), reached without touching either patched
  path.

So the answer to the brief's re-attack on the two silent-failure paths is: the shapes are
still there, one layer down, and the patch sits above them. A fix would have
`collect_repo_facts` return its failures as data (e.g. a `facts_incomplete` reason
alongside `RepoFacts`) so the rule can distinguish "no records" from "could not count
records", rather than the caller guessing from an exception that the callee is designed not
to raise.
