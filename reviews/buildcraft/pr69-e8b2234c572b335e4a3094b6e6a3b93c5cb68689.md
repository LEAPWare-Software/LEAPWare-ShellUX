## What the PR does

`scripts/lwb_check_proof.py`'s gate `check_pr_has_record()` normally requires
every PR to carry a `proof/*.json` record naming its own PR number. Dependabot
PRs (#60, #61) can never satisfy this, so they are permanently red on the
`lwb-proof-pr` CI check. This PR adds `is_bot_pr_author(login)` (matches a
GitHub login ending `[bot]`) and threads a `--pr-author` flag from
`.github/workflows/ci.yml` (`${{ github.event.pull_request.user.login }}`)
through to `check_pr_has_record()`, exempting a recognized bot author from the
self-record requirement, with an always-printed `NOTICE:` line, while
`check_new_proof_records_declare_pr` and every other gate is stated to still
bind bot PRs.

## Findings

**F1 (blocking): the exemption is keyed on who opened the PR, not on who
authored the commits under review.** `github.event.pull_request.user.login`
names the PR opener and does not change if a human with write access pushes
further commits onto a Dependabot-opened branch. The exemption code never
inspects the commit range at all. Reproduced directly against the real CLI:

```
$ git log -1 --format=%an\ %ae 9fd0a9153f56d69780f6f07b6e9afb7bd2d8548e
<human test author>   # commit adding scripts/smuggled.py, layered on the PR head
$ python3 scripts/lwb_check_proof.py --pr 999 --base <PR head> \
    --head 9fd0a9153f56d69780f6f07b6e9afb7bd2d8548e --pr-author 'dependabot[bot]'
NOTICE: pr-authority: PR #999 author 'dependabot[bot]' is a recognized bot account -- exempted from carrying its own proof record
lwb-proof check passed (24 record(s))
exit=0
```
A human-authored code change riding on a bot-opened PR passes the proof gate
with no proof record for it. The PR body and `lwb_lanes.py`'s docstring both
say bots "remain bound by every other check", but this specific check is
scoped to PR-opener identity, not to per-commit authorship the way
`lwb_lanes.py`'s own `BOT_AUTHOR_PATTERNS` check is (commit-email based). It
is plausible (not independently confirmed here) that `lwb_lanes.py`'s
separate commit-email gate would still catch such commits on its own path,
but that is a different, uncoordinated gate, and nothing in this PR states or
tests that reliance. Minimal fix: only exempt when every commit in
`base..head` also matches `BOT_AUTHOR_PATTERNS`, or otherwise document and
test the dependency on the commit-email gate explicitly. This is a real,
demonstrated hole in the door this PR adds, not a hypothetical.

**F2: the "never silent" claim holds only at the function level, not through
`main()`.** Mutation-tested by editing a temporary copy of `lwb_check_proof.py`,
running the full suite, then restoring the file (working tree left clean):
```
M8: main() calls check_pr_has_record(pr_author=..., notices=None)
    instead of threading notices=notices
=> 617 passed  (no test failed)
```
If `main()` stops threading `notices=`, the exemption becomes completely
silent in real CI runs and all 617 tests still pass.
`test_main_threads_pr_author_through_to_check_pr_has_record` swaps in a fake
`check_pr_has_record`, so it cannot observe whether the NOTICE is actually
printed on stdout — it is exactly the "found nothing" / "could not check"
conflation this repo's own standing rule warns against, just moved one layer
up from where the earlier internal reviews checked it.

**F3: the workflow-wiring test is weak and its self-described mutation check
is tautological.** Confirmed by running the actual test and by direct
mutation against the real `ci.yml`:
```
M1 (delete the --pr-author line from ci.yml)
    => FAILED tests/test_workflows_parse.py::test_lwb_proof_pr_step_passes_pr_author
M2 (change ${{ github.event.pull_request.user.login }} -> ${{ github.actor }})
    => 617 passed, nothing failed
M3 (change to ${{ github.event.pull_request.author.login }}, evaluates empty)
    => 616 passed, 1 deselected (flaky test excluded), nothing failed
M4 (--pr-author "" literal)
    => 617 passed, nothing failed
```
The test only asserts the parsed step's `run` string contains the substring
`--pr-author`, not the specific expression. M2 silently changes the
exemption's meaning (on a manual workflow re-run, a human re-runner would be
treated as "the author" instead of the PR's actual opener) with a fully green
suite. M3/M4 fail closed today (exemption becomes inert, #60/#61 stay red)
but only by accident of what an empty string does downstream, not because
anything pins the value. The PR's own description of a "mutation probe" for
this guard (checking that a string with the flag stripped no longer contains
the flag) tests Python's `in` operator on a string the test itself
constructs and proves nothing about the real file.

**F4 (matches, independently reproduced): the `$` anchor on `BOT_LOGIN_RE`
is unenforced by any test.**
```
M5: \[bot\]$ -> \[bot\]  (drop the trailing anchor)
=> 617 passed, nothing failed
```
Not exploitable today (GitHub logins cannot contain `[` or `]`, unverified
against GitHub's own login character-set documentation here), but the
anchor's own inline comment claims it as the reason a login like
`robot-wrangler` is rejected, and nothing pins that specific property.

**F5 (independently reproduced, genuinely pre-existing): an intermittent
failure in `tests/test_lwb_lanes.py`, unrelated to this PR's diff.** Run 15
times on each ref:
```
pr69-head (e8b2234): pass=13 fail=2
main      (0d1be71): pass=14 fail=1
AssertionError in test_is_record_only_commit_true_for_a_merge_with_empty_first_parent_diff
```
`resolve_reviewable_head` walks `git log --format=%H <head>` without
`--first-parent`; when a side-branch commit lands in a later second than the
mainline "substantive" commit, the walk returns the side commit first and the
assertion fails. Reproduces on unmodified `main` at a similar rate, so it is
not attributable to this PR. Consistent with BuildCraft's own internal
reviewers' attribution to PR #63 (`resolve_reviewable_head must walk
first-parent history only`), though this review did not independently
confirm that #63's code fixes it — only that the failure reproduces
identically off this PR's own change.

**F6 (independently reproduced, but the internal reviews overstate it): the
`--reexecute` digest mismatch on `proof/39.json` is pre-existing, but does
NOT reproduce with an identical digest.**
```
pr69-head: FAIL proof/39.json: python3 scripts/lwb_handoff.py --check
           (sha256 ded08fb2... != recorded ab8f5e3b...)   exit=1
main:      FAIL proof/39.json: python3 scripts/lwb_handoff.py --check
           (sha256 475224736... != recorded ab8f5e3b...)  exit=1
```
Both fail against the same stale recorded digest, but the two live re-run
digests differ from each other because this PR edits `HANDOFF.md` and
`lwb_handoff.py --check`'s output embeds `HANDOFF.md`'s byte count. The
failure mode is pre-existing and not this PR's fault, but "reproduces
identically" (as stated in BuildCraft's own internal review records) is not
quite accurate — the specific wrong digest changes. This step is currently
`continue-on-error: true` and blocks nothing today; flagged as relevant to
PR #62, which is said to make it blocking.

**F7: `verifiable: false` flips in `proof/69.json` hold up on inspection, not
just on the PR's own explanation.** `scripts/lwb_sanitise.py` normalises only
paths, not pytest timing output, and the recorded pytest tail
(`4 passed, 34 deselected in 0.13s`) genuinely varies run to run (re-run here:
`... in 0.06s`), so `nondeterministic-output` is an honest label for those
commands, though imprecise (the variation is state-dependent, not truly
random). The `lwb_check_commit_identity` flip to
`git-range-not-reproducible` was not independently re-derived here — flagged
as unchecked, not confirmed.

**F8: the proof record undercounts the test suite it is claimed to cover.**
`proof/69.json` (taken against commit `64a8d1e`) records "615 passed" and
"3 passed" for `test_workflows_parse.py`; the actual head (after `fe0ee15`
added tests responding to earlier review findings) has 617 tests total and 4
in that file. The proof record describes an earlier tree than the one this
PR is asking to merge.

**F9: `check_new_proof_records_declare_pr` does still bind a bot-exempted PR**,
confirmed directly rather than assumed:
```
$ python3 scripts/lwb_check_proof.py --pr 60 --base <main> --head <PR head> \
    --pr-author 'dependabot[bot]'

FAIL: proof/69.json: is new in this PR but self-declares 'pr' (69) instead of 60 ...

```
And the exemption fails closed on empty/missing author, never silently:
```
$ python3 scripts/lwb_check_proof.py --pr 60 --base <PR head> --head <PR head> --pr-author ''
FAIL: PR #60 carries no proof/*.json record for itself   exit=1
$ python3 scripts/lwb_check_proof.py --pr 60 --base <PR head> --head <PR head>   # flag absent
FAIL: PR #60 carries no proof/*.json record for itself   exit=1
```

## What would move this review to AGREE

1. F1 fixed: scope the bot exemption to PRs whose entire commit range is
   bot-authored (reuse `BOT_AUTHOR_PATTERNS`), or explicitly test and
   document that `lwb_lanes.py`'s separate commit-email gate is relied on to
   catch a human commit riding a bot-opened PR.
2. A `main()`-level test (not a substituted fake) asserting the literal
   `NOTICE: pr-authority: ...` line appears on stdout for a bot PR. Closes F2.
3. The workflow test pinned to the exact expression
   `--pr-author "${{ github.event.pull_request.user.login }}"`, not a
   substring match. Closes F3.
4. A test case for a login with `[bot]` not at the end (e.g. `x[bot]y`).
   Closes F4.
5. A refreshed `proof/69.json` test count matching the merged head. Closes F8.

Not blocking, but worth filing: F5 (recommend landing #63 to remove the
intermittent), F6 (correct "reproduces identically" to "same failure mode,
different digest" if it is written down again), F8 (regenerate the proof
record before merge).

Not checked:
- Real GitHub Actions execution, including whether `user.login` is populated
  on a fork PR or on a `merge_group` event (the step only fires on
  `pull_request`).
- Whether `lwb_lanes.py`'s commit-email gate actually catches the F1 scenario
  on a real bot-opened PR with a human commit layered on (plausible, not
  confirmed).
- Windows and macOS CI legs; Python 3.10.
- `reviews/69/*.json` record shapes against `reviews/README.md`'s format
  rules, and whether the three internal reviewer identities are genuinely
  distinct sessions (reviews/README.md's own stated residual: unknowable
  from inside the repo either way).
- The `HANDOFF.md` diff content itself.
- `.github/workflows/auto-queue.yml` beyond a grep for PR-creation triggers.
- GitHub's own documentation on which characters a login may contain.
- `scripts/lwb_check_env_leak.py` (requires a private-needle secret this
  review does not have).
- `lwb_check_commit_identity`'s `git-range-not-reproducible` flip, taken as
  plausible but not independently re-derived (see F7).
