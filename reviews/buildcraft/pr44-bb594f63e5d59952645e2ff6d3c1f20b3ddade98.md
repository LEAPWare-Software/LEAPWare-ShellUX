### CONFIRMED mechanism, PLAUSIBLE in practice 5. A single failing PR in the 15-minute sweep can starve every PR queued after it

`EXIT_NOT_READY=0`, `EXIT_ERROR=1` (`scripts/cloud/auto_queue.py:63-64`); the "Enqueue if ready" step has no `shell:` key, so per GitHub's documented default it runs as `bash -e {0}`. Simulated:
```
$ bash -e step.sh   # loop over 46,45,44; PR 46 exits 1
::group::PR #46
evaluated 46
step exit=1   (loop stops; 45 and 44 never evaluated)
```
Before this PR the job normally saw zero or one PR (from a single `check_suite`); the new sweep passes every open PR, newest first by GitHub's default ordering. A green-but-rejectable PR (merge conflict, already queued), an unreadable `pulls/{n}`, or a race with a concurrent `workflow_run` invocation would each block every older PR behind it for that run. Not verified against a live runner or GitHub's actual re-enqueue error behavior.

### CONFIRMED 6. A malformed dispatch input now succeeds silently instead of failing loudly — the "checked and found nothing" vs. "could not check" shape

```
--- pr_number=#44:  prs=   exit=0   stderr: NOTICE: could not resolve pull requests for this event
--- pr_number=²:    exit=1   ValueError: invalid literal for int() with base 10: '²'
```
On `main`, `pr_number=#44` used to emit `prs=#44`, which `main()` rejected loudly (`FAIL: LWB_PR_NUMBER is not set to a number`, red run). After this PR it produces a green run that silently does nothing, with the only signal on stderr where the sweep's own automation won't surface it. (`²` still fails loudly since `str.isdigit()` accepts it but `int()` doesn't — inconsistent handling of two malformed-input shapes.) The `commits/{sha}/pulls`-lookup-failure → `prs=` → green-run path is intentional and pinned by an existing test, but shares the same representation problem: a real lookup failure is indistinguishable, at the level anyone actually watches (the job's pass/fail color), from "no PRs need attention."
