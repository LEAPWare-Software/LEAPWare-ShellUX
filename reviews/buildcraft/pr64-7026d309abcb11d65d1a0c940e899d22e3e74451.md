## Findings

### Confirmed — the byte-identical port claim is true, verified by blob sha

`git rev-parse pr-48:<path>` equals `git rev-parse pr-64:<path>` for all four
carried-forward files. `scripts/lwb_lanes.py`, `tests/test_lwb_lanes.py` and
`scripts/githooks/commit-msg` are byte-identical to `origin/main` on this
branch and differ from #48's branch — confirming the claim that reapplying
#48's stale copies would have regressed `main`'s already-landed #56 fix.

### Confirmed — commit identity fix is real

`git log --format='%an <%ae>' origin/main..HEAD` returns exactly one line,
`LEAPWare <leapware@outlook.com>`, across all three commits including the
later independent reviewer's own record-only commit. `lwb_check_commit_identity.py
--base origin/main --head HEAD` exits 0.

### Confirmed — the B1 loop-abort fix works and is guarded by a real test

Extracted the "Enqueue if ready" `run:` block and ran it under `bash -e`
against PRs `11,22,33` with #11 forced to fail: shipped version attempts all
three PRs, step still exits 1; with `|| rc=1` removed, only #11 is attempted
before the script aborts. Removing `|| rc=1` and `exit "$rc"` together fails
`tests/test_workflows_parse.py` (1 of 8 failed).

### Confirmed, not blocking — F1: `isdigit()` accepts non-ASCII digits

`resolve_pr_numbers` (unchanged from #48, same blob) uses `str.isdigit()`,
which is `True` for `'²'` (raises `ValueError` in `int()`, uncaught — the
step dies instead of the documented `prs=`/exit-0 retry contract) and for
`'١٢٣'` (silently resolves to PR #123). Reproduced directly against the
shipped function. Severity low: only reachable via `workflow_dispatch`,
which requires repo write access, and the more common failure mode (raise)
fails loud rather than silently. Not introduced by this PR — same blob as
#48 — and not fixed here either.

### Confirmed, not blocking — F2: `proof/64.json`'s `commit` field names a nonexistent object

`6385feb9eb4d54b9ec62ec3e4e65cb0246f48de1` does not exist in this repository
(`git cat-file -t` fails, remote does not have the ref either).
`lwb_check_proof.py --pr 64` passes the record anyway — nothing mechanical
checks a proof record's `commit` field against the repository. The record's
own `unproven` note discloses this candidly, though the embedded reviewer's
record overstates the constraint (a resolvable value, e.g. the last commit
that actually touches the deliverable, was available and not used).

### Confirmed, not blocking — F3: the B1 regression test accepts a version of the loop that swallows every failure

The test's `exit\s+\$\?` assertion is satisfied by a line placed after the
loop, where `$?` is always the exit code of the preceding `echo`, not the
loop's own result. A scratch mutation (`auto_queue.py || true` inside the
loop, `exit $?` after) still passes `tests/test_workflows_parse.py` (8/8)
while reporting success even when every enqueue attempt failed. The shipped
YAML itself is correct (verified above); the regression test's actual
coverage is narrower than its docstring claims.

### Plausible, not reproduced — F4: the 15-minute sweep may repeatedly re-enqueue an ejected or already-queued PR

`main()` checks open/non-draft/targets-main/all-required-checks-green but
never whether the PR is already in the merge queue or was ejected from it.
Before this PR only a manual dispatch could enqueue; now every open PR is
retried every 15 minutes. Did not verify how GitHub's `enqueuePullRequest`
actually responds to a PR that is already queued, so this is not confirmed
as a real failure — flagged as a design question worth the owner's
attention given the automation now runs unattended.

### Plausible, minor — F5: the sweep's PR listing has no pagination

`pulls?state=open&base=main&per_page=100` silently caps at 100 with today's
~20 open PRs unaffected. Noted for completeness, not urgent.

### Noted, not attributable to this PR — one CI leg failed for a reason unrelated to this PR's content

`test (windows-latest, 3.12)` failed its own test step (not just
`lwb-lanes`) on the reviewed head. The sibling PR #46 shows an identical
one-platform-only pattern (macOS/3.12) that did not reproduce on re-run of
the same CI run. `origin/main` and several other open PRs are green on all
six legs. This is evidence the failure isn't attributable to either PR's
diff, not evidence of what it is — worth someone with CI log access looking
at before merge, since `lwb-lanes` clearing does not turn that leg green.
