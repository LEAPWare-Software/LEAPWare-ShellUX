### V1 [CONFIRMED, blocking] The rewritten workflow-safety guard still passes on the likelier form of the hazard it names

```

```
`on: pull_request` + `permissions: pull-requests: write` + `ref: ${{ github.event.pull_request.head.sha }}` — running PR-controlled code under a write token, the exact hazard the test is named for — ships green. The unpinned form is now caught; the pinned form, which is what someone would actually write, is not. Fix: assert the resolved `ref` equals the default branch, not merely that a `ref` exists.

### V2 [CONFIRMED, blocking] The merge path cannot enqueue anything a real reviewer produces, because it compares against the wrong head
`scripts/lwb_auto_queue.py::review_records` tests `head.startswith(reviewed)` against the **raw** PR head from the GitHub API. `scripts/lwb_lanes.py::resolve_reviewable_head` deliberately does not do this, and its own docstring says why: committing a review record advances the head past the sha the record names, so a committed record can never match the raw head. Reproduced against this PR's real history:
```

REVIEWABLE head (lanes) 665d12e09787016c14f530a049249c3e06c4577f
auto_queue verdict      NOT READY ["reviews/29/cloud-reviewer.json: reviewed_commit 665d12e09787 is not this head"]
```
That record was a valid, fresh AGREE naming the correct reviewable head under `lwb_lanes`' own rule — `lwb_lanes` would accept it, `lwb_auto_queue` refuses it. The moment a required review record lands (as this repo's own protocol requires it to, as a commit), the auto-queue path reports "not this head" permanently. The PR's central deliverable — an Actions job that can enqueue a reviewed PR — cannot do so under this repository's own review protocol; acceptance criterion 1 in `proof/29.json` ("moves the enqueue inside GitHub Actions," `met: true`) is not supported. Fails in the safe direction (stalls, never wrongly merges), but the feature does not work.
