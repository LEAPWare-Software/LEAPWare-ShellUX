## Findings

### 1. Non-blocking, pre-existing on `main`: proof-only and reviews-only commits are invisible to the review-staleness walk

`resolve_reviewable_head` skips any commit that touches only `proof/` or
`reviews/` (`_is_record_only_commit`). On this branch that means 358fba1
(a proof-only edit) sits after the reviewed commit f55b72d without
requiring a fresh review, and — separately — a probe run confirmed
`lwb_lanes.py` reads `reviews/` off the *working tree*, not `--head`:
running `--head 358fba1` in a long-lived local clone that still has
`reviews/74/cloud-reviewer.json` on disk wrongly reports the gate as
passing for that earlier head. GitHub Actions checks out the head commit
per job, so CI itself is unaffected; this is a hazard only for anyone
re-deriving the gate result locally from a persistent checkout. Not
introduced by this PR — `_is_record_only_commit` and the working-tree read
both predate it.

### 2. Non-blocking: one wording slip inside the proof record's own honesty section

`proof/lwb-recut-73-stale-disagree.json`'s last `unproven` entry
(line 111) calls 8b418ea "the earlier content+proof commit"; 8b418ea is
actually the content-only commit, and f55b72d is the one that adds the
proof record. The record's own `commit` field also names 8b418ea while
acceptance criterion 2's text describes what f55b72d did. This is a prose
inaccuracy inside a section whose whole purpose is self-correction, but no
gate or count depends on which of the two commits is named there.

### 3. Investigated in depth, not blocking: the tip commit's own internal review record is exactly the self-review shape BuildCraft's `reviews/README.md` documents as undetectable by the gate — but platform evidence outside the repo supports its independence

The tip commit (b803381, author `LEAPWare <leapware@outlook.com>`,
`LWB-Agent: claude`, `Claude-Session: session_013foGduP8gdf37p8gPmSAJh`)
adds `reviews/74/cloud-reviewer.json`, self-declaring
`reviewer_id: reviewer-cloud-routine-buildcraft-013foGduP8gdf37p8gPmSAJh-
2026-09-26`, `commit_author_id: claude-code-sonnet5-session-01Wgm1qF-
2026-09-26`, `verdict: AGREE`, `reviewed_commit: f55b72da...`,
`reviewer_was_dispatched_by_author: false`. This is what turns BuildCraft's
own `lwb-lanes` gate green — confirmed directly:
`lwb_lanes.py --base origin/main --head HEAD --pr-number 74` passes at the
current head, but the same command against a checkout of 358fba1 (the
commit immediately before this record existed) fails three times with
`touches a shared path and has 0 independent review(s) in reviews/74/,
needs 1`.

Per `reviews/README.md`'s own text, `reviewer_id`/`commit_author_id` are
self-attested strings, and the file documents — with its own measured
history (PRs 15-17) — that a record can look independent while sharing the
same underlying session under a different-looking dispatch id, a case its
own `MIN_SHARED_SEGMENT_LENGTH` heuristic can miss. Checked here: the two
ids' segment sets (`{reviewer,cloud,routine,buildcraft,
013foGduP8gdf37p8gPmSAJh}` vs `{claude,code,sonnet5,session,01Wgm1qF}`)
share nothing at or above the 8-character floor, so the repo's own gate
would not flag this pairing even if it were a disguised self-review — the
gate's textual check gives no information either way here. Git history
inside BuildCraft alone cannot settle it: HANDOFF item 2 already records
that a #27 "cloud-routine" reviewer was in fact fired by its own author's
session, so the role name `reviewer-cloud-routine-buildcraft` proves
nothing by itself, and commit trailers are self-attested like every other
identity field this file warns about.

What does settle it, to the extent anything outside the repository can:
platform session and trigger records (not writable by a PR author) show
the reviewer session (`session_013foGduP8gdf37p8gPmSAJh`, title "BuildCraft
independent reviewer", origin `scheduled_trigger`, created
2026-09-26T06:23:41Z, model claude-opus-5) is a different process from the
author session (`session_01Wgm1qFPafv1nA5vc7BSPRE`, title "BuildCraft
conductor (track A)", created 04:11:50Z, model claude-sonnet-5), fired by
a distinct hourly trigger (`trig_01RcTdw6nbX2Tj9gFwmcZe8G`, schedule
`23 * * * *`, created 2026-09-19, a week before the author session
existed, generic prompt not aimed at #74) rather than by the conductor's
own trigger (`trig_015C7Q5ZE7KrkzztEJAb8jvC`, schedule `11 */2 * * *`).
Both routines share one account and one environment, so this shows two
separate scheduled processes, not two separate people, and a manual
`fire_trigger` landing on the exact scheduled second cannot be ruled out
from outside. Plain conclusion: on the evidence the BuildCraft repository
itself holds, this record is indistinguishable from a self-review — the
exact residual weakness `reviews/README.md` already names. It is not, on
the fuller evidence available to this review, actually a self-review. That
distinction rests on platform records outside BuildCraft's own gate, which
is precisely the gap the gate's own documentation says it cannot close on
its own.

Separately, the record's choice to cite `reviewed_commit: f55b72d` rather
than the branch's raw tip is correct, not a second gate trick: probes
confirmed a record naming 358fba1 (the tip) or 8b418ea is rejected as
STALE against `resolve_reviewable_head`, which returns f55b72d for this
branch (358fba1 and b803381 both touch only `proof/`/`reviews/`). A second
record with `verdict: DISAGREE` was also confirmed to still block the gate
(`verdict is 'DISAGREE', want 'AGREE'`), so the gate is not merely
majority-vote over records.

### 4. Low, not introduced here: the commit-identity check reads author, not committer

The first three commits on this branch carry author `LEAPWare
<leapware@outlook.com>` but committer `Claude <noreply@anthropic.com>`.
`lwb_check_commit_identity.py` reads only `git log --format=%an\t%ae` and
passes as designed; no repository rule constrains the committer field
separately. Not the same defect as HANDOFF item 3's #49 case (which was
about the author field itself being wrong), so no action indicated.
