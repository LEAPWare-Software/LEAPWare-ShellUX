8. **The new guards, read directly, are a guardrail (name-specific
   substring match), not an integrity control — and this is exactly how
   the PR itself describes them.** Both `scripts/lwb_check_proof.py` and
   `scripts/lwb_record.py` match the bare substrings `lwb_handoff` /
   `lwb_check_state_claims` case-insensitively against each `argv`
   element, for records at `effective_pr >= 20`. Tested directly against
   `_command_reads_mutable_generated_state`:
   ```
   True  ['python', 'scripts/lwb_handoff.py', '--check']
   True  ['python', '-m', 'pytest', 'tests/test_lwb_handoff.py', '-q']
   True  ['python', 'scripts\LWB_HANDOFF.PY']
   True  ['python', '-m', 'lwb_handoff']
   True  ['sh', '-c', 'python scripts/lwb_handoff.py --check']
   False ['python', 'scripts/lwb-handoff.py']
   False ['make', 'handoff-check']
   ```
   The two `False` spellings don't exist anywhere in the repo (`ls
   scripts`, grep of Makefile/toml/cfg/sh/json outside `proof/`/`reviews/`
   found no alias), so nothing today slips through, but any wrapper or
   indirection would bypass the match. The match is also broader than the
   PR description states — it also catches `--help` and pytest runs of
   `test_lwb_handoff.py`, which are actually deterministic — but nothing
   currently marks those `verifiable: true`, so this is over-inclusive by
   design and harmless today, not a live defect. Malformed/missing
   `verifiable` (e.g. `1`, `"true"`) is rejected by the existing
   `isinstance(verifiable, bool)` check, so a "could not check" case does
   not silently pass as a check that found nothing.

9. **New regression tests are not vacuous.** Broke both matchers (`return
   False`) in a scratch worktree; 5 of the new tests failed exactly as
   expected, the rest (41) passed:
   ```
   FAILED test_handoff_check_marked_verifiable_true_is_rejected
   FAILED test_handoff_check_module_form_marked_verifiable_true_is_also_rejected
   FAILED test_check_state_claims_marked_verifiable_true_is_rejected
   FAILED test_run_command_rejects_verifiable_true_for_lwb_handoff_check
   FAILED test_run_command_rejects_verifiable_true_for_lwb_check_state_claims
   ```
   Tests call the real `_validate_record`/`run_command`, not mocks, and
   cover both directions (reject `true`, accept `false`/unrelated
   commands). One unverified (PLAUSIBLE) gap: the recorder test's
   docstring claims the guard fires "before... subprocess.run", but no
   test patches `subprocess.run` to prove ordering; the code as written is
   correct, this is a test-strength note only.

10. **The disclosed honesty gap is real; one part of its own mitigation
    claim is slightly generous.** `REEXECUTE_EXIT_NOTHING_REEXECUTED = 2`
    is live code (`reexecute_exit_code` returns it when
    `total_reexecuted == 0`; `main` propagates it), not dead code as one
    might suspect from a "disclosed but unenforced" framing. But the count
    is repo-wide: a single new record marking everything `verifiable:
    false` still passes overall since older records keep the total above
    zero — only that record's own printed line (`0 of N commands
    re-executed`) would show it. "Visibility, not prevention" (the PR's own
    words) is accurate; "the exit code... makes that visible" slightly
    overstates it, since for a single record that exit code can never fire
    in practice. Disclosure-precision point, not a defect.
