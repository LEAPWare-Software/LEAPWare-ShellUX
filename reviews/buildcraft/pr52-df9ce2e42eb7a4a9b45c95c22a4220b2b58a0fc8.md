Verdict: DISAGREE

The rule is registered, it ships at `warn`, the vendor copies match the source, and the suite passes. But it has bypasses the PR does not disclose. One of them lets an allowed action cover a disallowed one in the same command, which matters for a rule that is meant to deny later. It also has false positives on everyday commands, and one "What I ran" claim in the PR body is false at the head commit.

All probes below ran against the PR head (df9ce2e) with a throwaway script calling `_classify_command` and `evaluate` directly, passing a `RepoFacts` object and `mode=WARN`. Nothing was run against a real repository. Everything listed as CONFIRMED was reproduced.

## Findings, worst first

**1. CONFIRMED, undisclosed: an allowed action anywhere earlier in a command hides the unauthorised action after it.**
- **Cause:** `_classify_command` (rule file lines 293–304) returns only the first destructive segment. `evaluate` then checks whether that one segment is allowed. If it is, the function returns None and never looks at the later segments.
- **Probe output:**
  - `git push origin --delete landed && git push -f origin main` with `verified_landed_branches=["landed"]` gives `(('delete_ref', 'landed'), 'silent')`.
  - `git reset --hard origin/main && git push -f origin main` with `allow.history_rewrite=True` gives `(('history_rewrite', None), 'silent')`.
- **Impact:** once the rule is armed to deny, any force-push goes through if it is chained after an allowed action.

**2. CONFIRMED, undisclosed: an allow for one category also authorises a different category in the same `git push`.**
- **Cause:** force-push is checked before delete in the classifier (lines 247–258). A push that both forces and deletes is classified only as `force_push`.
- **Probe output:**
  - `git push -f origin --delete main` with `allow.force_push=True` gives `(('force_push', None), 'silent')`.
  - `git push --force-with-lease origin :main` with the same setting gives `(('force_push', None), 'silent')`.
- **Impact:** deleting `main`, which the hard rules say always needs the owner, is authorised by the `force_push` allow. This is the case the brief described: a field is read while a sibling that changes its meaning is ignored.

**3. CONFIRMED, undisclosed: deleting several refs at once only checks one of them against `verified_landed_branches`.**
- **Cause:** the `--delete` path checks only the last positional argument (line 257). The `:ref` path checks only the first one (lines 259–261).
- **Probe output:**
  - `git push origin --delete main landed` gives `(('delete_ref', 'landed'), 'silent')`.
  - `git push origin :landed :main` gives `(('delete_ref', 'landed'), 'silent')`.
  - In both cases `main` is deleted with no finding.
- **Related gaps:**
  - `refs/heads/landed` does not match a list entry of `landed`, which produces a false finding.
  - Nothing stops a policy from listing `main` or a tag name. The hard rule excludes both from the carve-out explicitly.

**4. CONFIRMED, undisclosed force-push and ref-deletion shapes.** All of these returned `((None, None), 'silent')`:
- `git push origin +main` and `git push origin +HEAD:main`. A `+refspec` is git's standard way to force a push.
- `git push -uf origin main`. Short flags combined into one token are not recognised.
- `git push --mirror origin`. This force-updates and deletes remote refs.
- `git push --prune origin 'refs/heads/*:refs/heads/*'`. This deletes remote refs.

The disclosed list covers `-C`, env-prefixed pushes, `git.exe`, scripts and aliases. None of the shapes above is on it.

**5. CONFIRMED, undisclosed: settings changes on paths the rule claims to recognise still get through.** All returned silent:
- **Implied POST:** `gh api repos/o/r/rulesets -f name=x -f enforcement=disabled` and `gh api repos/o/r/branches/main/protection --input p.json`. `gh` defaults to POST whenever `-f`, `-F` or `--input` is given, but `_gh_api_method` returns None unless `-X` or `--method` is present.
- **Method glued to the flag:** `gh api -XPATCH repos/o/r -f visibility=public`.
- **Quoted path:** `gh api -X PATCH 'repos/o/r' ...` and `gh api --method DELETE "repos/{owner}/{repo}/rulesets/7"`. `_strip_quoted` replaces the quoted span with a space, so the path never reaches `_looks_like_settings_path`. Quoting is normal whenever the path contains `{owner}`.

The disclosed blind spot is "a path that is not one of the recognized shapes". These are the recognised shapes.

**6. CONFIRMED false positives, which would push users to ignore the rule before it is armed:**
- `git rebase --abort` and `git rebase --continue` are both flagged as `history_rewrite`. An abort undoes a rewrite; it does not perform one.
- `git fetch && git reset --hard origin/main` is flagged as `history_rewrite`. That is a routine local sync that changes no published history.
- `gh api -X POST repos/o/r/issues -f title=docs/protection` is flagged as `settings_change`. Line 283 scans every token that does not start with `-`, including flag values, and matches the `/protection` substring.

None of these are tested.

**7. CONFIRMED, partly disclosed: `-n` silences real rewrites.** `_NON_PUBLISHING_FLAGS` treats `-n` as "dry run" for every subcommand, but in these two commands it means something else:
- `git commit --amend -n -m x` (here `-n` is `--no-verify`) returns silent.
- `git rebase -n origin/main` (here `-n` is `--no-stat`) returns silent.

The docs say `-n` anywhere in a segment skips it, but they do not say this hides real amends and rebases.

**8. CONFIRMED: the rule goes silent on absent or incomplete repo facts, although it reads no repo fact.**
- **Probe output:** `gh repo delete o/r --yes` at `mode=DENY` returns `None` both with `repo=None` and with `facts_incomplete=True`.
- **When `repo` is None:** `adapters/claude/repo_facts.py:659-661` (`collect_repo_facts`) returns None whenever the working directory is not inside a git repository. So from a non-repo working directory, `gh repo delete` and `gh api` settings changes (which need no local clone) are never reported.
- **When facts are incomplete:** an unreadable proof directory turns off the destructive-action check.
- **Disclosure and reasoning:** the docs disclose Codex being always silent, but not the non-repo working-directory case. The stated reason ("absence of evidence") does not apply, because the classification uses only `tool_input` and `options`.

**9. CONFIRMED: the PR body's claim "`lwb_check_state_claims.py` → passed" is false at df9ce2e.**
```
FAIL: HANDOFF.md:54: [stale deliverable proof state in generated block] recorded=['22/22 proven', ...] re-derived=['23/23 proven', ...]
lwb_check_state_claims exit=1
```
Re-deriving independently with `lwb_handoff._proof_state_lines()` gives `['23/23 proven', ...]`. The commit that adds `proof/52.json` says it regenerated `HANDOFF.md` in the same commit, but the block still shows main's `22/22`. On `main`, the same checker passes. `lwb_handoff.py --check` passes on the PR (exit 0), so only the state-claims check catches it.

**10. PLAUSIBLE, and close to a disclosed blind spot:** wrapper and subshell forms return silent.
- Forms: `(git push -f ...)`, `{ git push -f ...; }`, `command git push -f`, `/usr/bin/git push -f`, `git -c k=v push -f`, `bash -c '...'`, `echo $(git push -f ...)`.
- Only `-C`, env-prefixed pushes, scripts and aliases are disclosed.
- **Also silent:** `gh repo archive` and `gh repo rename`, which are arguably settings changes.

**11. Minor docs issues:**
- The rule docstring (lines 125–128) says "four common, well-known subcommands" and then lists five.
- The docs' Modes table says `deny` means "The command is blocked" without saying that nothing is blocked when `repo` is None or facts are incomplete.

## Items from the brief that hold

- **Registration:** the rule is in `RULES` (`core/lwb_core/rules/__init__.py`) and ships at `"mode": "warn"` in `core/policy/default.json`.
- **Vendor build:** `python3 scripts/lwb_build.py --check` printed OK for both `plugins/claude/lwb/vendor` and `plugins/codex/lwb/vendor` (exit 0).
- **Tests:** `PYTHONPATH=core:adapters python3 -m pytest tests/ -q` gives `661 passed, 1 warning in 23.03s`. The new rule's tests plus the mutation tests give `75 passed`.
- **Other checks:** `lwb_check_prefix` and `lwb_check_no_instruction_dep` both exit 0.
- **Mutation tests are real:** the policy turns on only this rule, and the test asserts that its finding appears with the real `RULES` and disappears when the rule is filtered out. They would fail if the rule were removed.
- **Unit tests cover the happy paths only.** 29 test functions, and none covers findings 1–7. There is no chain whose first action is allowed, no multi-ref delete, no `+refspec`, no implied POST, and no `rebase --abort`.
- **Allowlist edge cases are safe.** An allow key with a hyphen typo (`force-push`), the string `"true"`, an empty or missing `verified_landed_branches`, or a string value in place of a list all produce a finding. None of them silently authorises.
- **Merge carve-out works:** `git merge --squash`, and `gh pr merge --squash --delete-branch`, are silent. `git merge feat && git push -f` still flags the push.
- **The four categories match** `docs/handoff-protocol.md` "## Hard rules" on `main`: settings, force-push, history rewrite, deleting a remote ref with the verified-landed carve-out, and merge excluded per D19. No fifth category was added. Build-plan item 1.6 matches.
