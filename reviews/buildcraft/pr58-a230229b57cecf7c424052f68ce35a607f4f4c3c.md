## Findings, most severe first

### 1. CONFIRMED, already on `main`, does not block this PR: the lane-ownership check never looks at files a merge commit edits

`scripts/lwb_lanes.py`'s `is_merge = len(_commit_parents(sha)) >= 2` turns off the per-file ownership check for every merge commit, including content that exists in neither parent (the merge author's own writing). Reproduced in a scratch repo: an agent tagged `LWB-Agent: codex` made a real `--no-ff` merge and, while resolving it, appended a line to a file in the `claude` lane — the ownership check passed (`errors: []`). The same edit as an ordinary commit is correctly flagged: `"... touches 'plugins/claude/lwb/bin/lwb_hook.py', outside the codex lane and not a shared path"`. This lets one lane's code be edited through a merge from another lane. Likely fix: exempt only files where the merge result matches a parent, and still run the ownership check on paths from `git diff-tree --cc <merge>`.

### 2. CONFIRMED, already on `main`, does not block this PR: `lwb_check_env_leak.py --range` cannot see content added while resolving a merge

It walks history with `git log -p`, which (git 2.43) prints no diff for merge commits (`git log -p -1 dd75f68 | grep -c '^diff --git'` → `0`). Reproduced in a scratch repo: a needle added while resolving a merge, then removed in the next commit, is invisible to `--range` (`lwb-env-leak check passed`, exit 0) even though the needle is still reachable at `HEAD~1`. The same leak made in an ordinary commit is caught correctly. **This PR's own merge is clean**: `git show --cc dd75f68` prints no hunks, so its resolution added nothing not already in one of its parents — this finding is about the checker's blind spot, not about this PR.
