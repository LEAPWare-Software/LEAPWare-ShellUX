## Findings (most severe first)

### CONFIRMED F1. `lwb_proof_coverage` warns about merges that CI counts as proven, including PR #49's own merge

- The hook checks the PR number against proof **filenames** only: `adapters/claude/repo_facts.py`, `collect_landed_unproven`, `known = set(known_ids)` then `if pr not in known`.
- CI checks the record's **contents** instead: `scripts/lwb_check_proof.py:557-565` does `if isinstance(data.get("pr"), int): proved_prs.add(data["pr"])`.
- `proof/README.md:61-76` documents records with a descriptive filename (not a PR number) that declare `"pr"` as a supported convention. This PR's own record is one of them: `proof/lwb-ship-proof-coverage-integrity.json` has `'pr': 49`.
- Reproduction (scratch repo, a loose commit `Ship thing (#49)` and `proof/lwb-ship-slug.json` = `{"pr":49,...}`):
  ```
  landed_unproven: ('31d6e3cfcda1 (#49)',)
  lwb_proof_coverage -> Finding(... '1 landed deliverable(s) reachable from HEAD have no matching proof record ... 31d6e3cfcda1 (#49)...')
  ```
- CI's coverage check accepts that same record. So once #49 is squash-merged, any clone that still has the merge as a loose commit will warn about #49 on every publish — a false warning, contradicting the docstring's "a missed warning, not a false one".
- The only test of a "matching record" (`test_a_squash_merge_subject_with_a_matching_record_is_silent`) uses `proof/41.json` (a PR-numbered filename). No test covers a record with a descriptive filename that declares `pr` — exactly the shape this PR's own proof record uses.

### CONFIRMED F2. An unparseable proof record for the branch satisfies `lwb_proof_required`, and `lwb_proof_integrity` stays silent — no rule reports it

- The integrity docstring claims: "A missing or unreadable record is `lwb_proof_required`'s territory." False: `lwb_proof_required` only checks that the filename exists (`known = set(repo.proof_ids)`, line 272), never that it parses.
- `collect_matched_proof_facts` turns a `ValueError` into `continue`, then returns `(None, None)` — the same representation as "no record exists".
- Reproduction (`proof/feat.json` = `{"author":"x","checked_by":"x", BROKEN`, event `git push origin feat`, all three rules forced to DENY):
  ```
  RepoFacts(branch='feat', proof_ids=('feat', 'lwb-ship-slug'), facts_incomplete=False, ..., matched_proof_self_certified=None, matched_proof_has_failed_command=None)
  lwb_proof_required -> None
  lwb_proof_integrity -> None
  ```
- A self-certified record is still sitting in the file, but truncation slips it past the one rule meant to catch it. `test_malformed_json_is_no_opinion_not_a_crash` asserts this silence as intended behaviour — the silence is the bug, not a regression from it.

### PLAUSIBLE, minor. Type holes in the failed-command check

- `{"exit":"1","expect_exit":0}` is not flagged (string vs int). CI's own schema would reject this record as malformed, so the exposure is narrow, but the rule itself has no opinion.
- `{"exit":true,"expect_exit":1}` is not flagged, because `True == 1` and `bool` is an `int` subclass in Python — matches CI's own comparison, so not a regression, but worth a named caveat.
- `checked_by: "x "` vs `author: "x"` is not treated as self-certification (exact-string compare, whitespace-sensitive) — again matches CI's behaviour.
