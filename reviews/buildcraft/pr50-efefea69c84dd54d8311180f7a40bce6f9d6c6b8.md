## Findings, most severe first

### CONFIRMED F1 (non-blocking). The path-traversal regression test passes even with the guard removed
`test_a_branch_name_that_would_escape_proof_dir_is_refused` never creates a `proof/` directory in its temp repo, so on POSIX a `tmp/proof/../secret.json`-shaped path fails to resolve regardless of whether `_branch_proof_path` rejects `..`. Confirmed by replacing the guard in memory with an unguarded path join (no file changed): `14 passed in 0.09s` — the mutant test suite still passes. Separately confirmed the guard itself works when `proof/` is made to exist: with `proof/` present and the guard removed, the crafted branch name reads `../secret.json`; with the guard restored, it correctly refuses. The test needs to create `tmp_path/"proof"` to actually exercise the code it claims to. Low severity in practice — git's own ref-format already forbids `..` in branch names, so reaching this code needs a hand-crafted `.git/HEAD`.

### CONFIRMED F2 (low). The `bool` half of the non-integer-`"pr"` regression test cannot fail
`test_a_non_integer_declared_pr_is_ignored_not_stringified` checks a `{"pr": true}` record; `str(True)` is `"True"`, which can never equal a squash-subject's `"77"`, so that half of the test passes whether or not the `not isinstance(pr, bool)` guard exists — confirmed by dropping the guard in memory: `18 passed in 1.11s`, unchanged. Only the string-`"77"` half of that test is a real regression guard.

### CONFIRMED F3 (non-blocking). `collect_landed_unproven`'s docstring overclaims parity with CI's `check_coverage`, in both directions
Built temp repos with the test module's own fixtures and ran both functions side by side:
- A record with no `pr` field and a non-matching filename: hook silent, CI warns (hook under-matches, the documented-safe direction — but a test (`test_a_squash_merge_subject_with_a_matching_record_is_silent`) already locks this specific shape in as "counts as proof").
- A branch-named record that names the squash commit's subject and hash but carries no `pr` field: hook **warns**, CI is silent (false positive the docstring explicitly says cannot happen).
- A record with `"pr": true` for the matching PR: hook **warns**, CI accepts it (CI accepts any `int` including `bool`; the hook's own `not isinstance(pr, bool)` guard rejects it) — another false-positive direction.
- A nested `proof/nested/x.json`: hook silent (only globs the top level), CI warns.

Currently latent: this repo's 22 real proof records all carry a plain integer `pr`, so none of the false-positive shapes occurs today. This is a doc-accuracy defect (the docstring states a parity claim that is not true), not a code defect at `mode: warn`.

### CONFIRMED F4 (low). Self-certification detection misses case and whitespace variants — pre-existing in CI too
`collect_matched_proof_facts` compares `checked_by`/`author` with exact `==`; `"Alice"` vs `"alice"` and `"alice"` vs `"alice "` both read as not-self-certified. CI's own `_validate_record` uses the identical exact comparison, so the new rule's claim to catch "the same signal CI rejects" is accurate as stated — the weakness is shared and pre-existing, not introduced here.

### CONFIRMED F5 (low). A malformed `commands[]` entry reads the same as a clean record
When `exit`/`expect_exit` are non-integer, `matched_proof_has_failed_command` returns `(False, False)` — indistinguishable from a genuinely clean record. CI's own validator rejects these shapes as schema errors; the hook's docstring already states it is not a full validator, so this is recorded as low rather than blocking, per this review program's standing concern about "found nothing" and "could not check" sharing a representation.

### CONFIRMED F6 (low, documentation gap). Neither new rule's doc states it is inert on Codex
`grep -rln "RepoFacts\|collect_repo_facts" adapters/ plugins/codex/` finds no Codex-side collector, so `event.repo` is always `None` there and both rules are silently inert on that adapter. `docs/rules/lwb-proof-required.md` already carries a "Known gap: Codex" section; `docs/rules/lwb-proof-coverage.md` and `lwb-proof-integrity.md` do not mention it. Deferred under D11 per existing project convention, hence low.

### PLAUSIBLE F7 (low). The bounded loose-object walk can both under- and over-count relative to CI in ordinary repo states
Reasoned from the code, not reproduced end to end: a fresh clone or any post-`git gc` state stops the walk at the first packed object, so in the common case the walk sees zero squash merges (the documented-safe under-count direction). A squash merge arriving via `git merge main` sits on a second parent a first-parent walk never visits (also under-count). Conversely, since the hook checks a fixed 40-commit window rather than CI's just-pushed range, a repo freshly adopting this plugin could see warnings on pre-adoption squash merges CI never flags, until exempted or the window ages past them. This repository's own 27-commit main history is small enough this is unlikely to bite here now.
