## Summary

The two named cases (`event.repo is None`, `event.repo.facts_incomplete`)
do now fail closed under `deny`, using the new, honest reason string, and
never the old "N record(s) found ... none matching" wording that caused
"Attack C". `warn`/`off` are confirmed unchanged. Policy files, `engine.py`,
and core I/O-freedom are all untouched as claimed. The new tests catch
real mutations of both new branches.

But two confirmed defects mean the fix does not deliver what it appears
to promise. The most serious (F1) is the *same class of bug this PR
exists to fix, inverted*: under `deny`, a repo whose facts are only
partially unreadable now denies with a reason claiming "could not
verify" even when the collector *did* read a matching proof record —
the new fail-closed branch fires before the existing match-check runs,
so a genuine positive is discarded and reported with a false-sounding
reason. The second (F3) is a docs regression: the base branch listed "a
corrupt HEAD" among `deny`'s documented remaining bypasses; at this PR's
head, that bypass is neither closed nor mentioned — it silently still
allows, and disappeared from both the "now fails closed" and "remaining
bypasses" lists. Given `CLAUDE.md`/this repo's own standard that a
security-relevant behavior change must not leave the docs claiming
something false by omission, and that this specific PR's entire point is
precision about which cases are and aren't handled, both are treated as
blocking.

## Findings

### F1 — CONFIRMED: `deny` can discard a genuine match and report a false "could not verify"

`facts_incomplete` short-circuits to the new fail-closed branch *before*
`_matching_record` is checked. Reproduced through the shipped hook: a
directory with `proof/51.json` present (a real matching record) and
`.git/HEAD` replaced by a directory (making `facts_incomplete=True`),
`deny` policy, `gh pr merge 51`:

```
"permissionDecision": "deny",
"permissionDecisionReason": "...could not verify whether a matching proof
record exists for '51': repository facts could not be fully read (could
not read .../.git/HEAD: IsADirectoryError...)"
```

With the identical repo and only `.git/HEAD` made readable, the result is
`{"permissionDecision": "allow"}` — record 51 was present in
`proof_ids` the whole time. The denial's own reason is false: the rule
did not fail because it "could not verify" — it had the answer and
didn't look. No test exercises "facts incomplete, but a matching record
is still visible" — every new test pairs incomplete facts with an absent
record. This is not a hypothetical edge case; it is the direct case this
PR's own Attack-C framing warns against, just moved from the allow side
to the deny side.

### F2 — CONFIRMED, non-blocking on its own: shipped hook messaging now contradicts `deny`'s behavior

`plugins/claude/lwb/bin/lwb_hook.py` still tells the user, on incomplete
facts, that rules needing repo facts "may have stayed silent for this
event" and that the rule "could not run for this event" — both now false
under `deny`, where the rule runs and actively denies. Not independently
blocking, but corroborates that this PR's user-facing surface was not
fully updated to match its own behavior change (rule 3, "documentation
lands in the commit that makes it true").

### F3 — CONFIRMED: a corrupt/empty `HEAD` still allows silently under `deny`, and the bypass was dropped from the docs rather than closed or disclosed

`read_branch_ex` returns `(None, None)` for any `HEAD` content that isn't
a well-formed `ref: refs/heads/...` line, which is indistinguishable from
a legitimate detached HEAD (`facts_incomplete` stays `False`) — and the
PR's detached-HEAD scope-out then permits it. Verified via the shipped
hook, `deny`, no proof record:

```
[valid branch]       -> deny, "0 record(s) found ... none matching"
[corrupt HEAD bytes] -> {"permissionDecision": "allow"}
[empty HEAD]         -> {"permissionDecision": "allow"}
```

The pre-PR docs listed "a corrupt HEAD" explicitly among `deny`'s
documented remaining bypasses. Post-PR, `grep -i corrupt` matches neither
the rule nor its docs page — it is present in neither the "now fails
closed" list nor the "confirmed bypasses that remain" list this PR
explicitly restructured. A known, still-open bypass silently disappeared
from the record during a PR whose whole purpose is to state precisely
which bypasses are and are not closed.

### F4 — PLAUSIBLE, non-blocking: several doc claims lack a pinning test

Deny-blocks-every-Codex-publish (follows from `repo is None` but
untested on the Codex adapter — the cross-adapter conformance suite has
no publish case); a crashed repo-facts collector failing closed (hook's
`repo_error` path under `deny` untested); a bare repository counting as
`repo is None` (untested, taken from reading the code).
