Reviewing LEAPWare-Software/LEAPWare-BuildCraft PR #44, "fix(cloud): auto-queue's trigger has fired zero times", base `main` (e5f29bfaccec90199f983b778c1d7689b8c24d33), at head `096cb59b556ea00fdb8848ec30452709b29687cb`.

The trigger-rewiring itself is sound — the `workflow_run` names match `CI`/`Handoff` exactly, the PR-resolution filter is correct, the cron is genuinely every 15 minutes, and the readiness logic (`_all_required_checks_green`, `enqueue`) is untouched. It fails review because the new `--find-prs` step reintroduces, one layer down, the exact silent-stall shape this PR exists to fix.

Findings:

1. **The `--find-prs` step writes diagnostic NOTICE lines into `$GITHUB_OUTPUT`, and on a lookup failure those lines are indistinguishable from a clean "no PRs" result** (the swallowed-exception-looks-like-a-negative pattern). The step is `run: python scripts/cloud/auto_queue.py --find-prs >> "$GITHUB_OUTPUT"`. `_api`'s and `emit_find_prs`'s `NOTICE:` lines go to stdout, so they land in `$GITHUB_OUTPUT` too, not just the job log. Reproduced with a fake `gh` that fails on PATH:
   ```
   == wr (gh fails) ==
        1  NOTICE: gh api repos/LEAPWare-Software/LEAPWare-BuildCraft/commits/abc123/pulls exited 1: HTTP 404: ...
        2  gh: second stderr line
        3  NOTICE: could not resolve pull requests for this event
        4  prs=
   -- lines with no '=' and no '<<' (runner-invalid): 1, 2, 3
   ```
   `resolve_pr_numbers` itself keeps `None` (lookup failed) distinct from `[]` (confirmed zero PRs), but `emit_find_prs` — its only caller — collapses both to `prs=` with exit 0, and the next step's `if: steps.find.outputs.prs != ''` treats them identically. A persistent lookup failure (bad token, API outage) becomes a 15-minute sweep that silently does nothing — the stall this PR set out to end, relocated rather than closed. Separately, lines without `=` or `<<` are (to the reviewer's understanding, not verified against a live runner — see Not checked) invalid `$GITHUB_OUTPUT` file-command syntax and may fail the step outright, contradicting the docstring's claim that lookup failure "prints `prs=` rather than failing the job."
   The new test `test_emit_find_prs_unresolved_prints_empty_prs_and_does_not_fail` does not catch this: it stubs `resolve_pr_numbers` directly, so `_api`'s NOTICE is never produced, and it asserts only `"prs=" in out` as a substring — which stays true even though the function's real output (with a real failing lookup) also contains a `NOTICE:` line with no `=`.
   Fix: send NOTICE/diagnostic lines to `sys.stderr`, and emit a separate `outputs` field (or a step annotation) so a caller — or a human — can tell "confirmed zero PRs" from "the lookup failed" without reading the log.

2. **Minor, confirmed: the schedule sweep reads only one page of open PRs.** A single `gh api ".../pulls?state=open&base=main&per_page=100"` call, no `--paginate`, no `Link`-header handling. At today's scale (3 open PRs) this is inert, but PR #101+ against `main` would never be swept, with nothing to indicate the cut-off.
