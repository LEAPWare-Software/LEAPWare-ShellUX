Summary: the claimed mechanics mostly check out — the suite does reach 601,
and the new tests genuinely fail on the old code for 7 of 9 cases. But the
merge-commit fix introduces a new false-pass path: a constructed repro gets
the complete `check_lanes` gate to report zero errors on a PR whose final
content no reviewer ever saw. The base code (pre-fix) correctly fails the
same repro. A review-freshness gate must not regress that way, so this
blocks regardless of the other findings.

## Findings, most serious first

**F1 (blocking): a record-only merge can put unreviewed content through the gate.**
`_is_record_only_commit` now skips a merge whose diff against its FIRST PARENT
is empty/records-only. But `resolve_reviewable_head` walks `git log <head>`,
which orders commits by commit date across BOTH sides of a merge, not by
first-parent-only traversal. So after skipping the merge, the walk can land on
a second-parent-side commit with different content and a fabricated (author-
controlled) later commit date.

Constructed repro (root `seed`; Q: `core/app.py=GOOD` on a side branch dated
3000; X: `core/app.py=EVIL` on main dated 2000; M: `git merge -s ours`,
carrying a valid AGREE record naming Q, dated 4000; every commit tagged
`LWB-Agent: claude`, `core/` is a shared path):
```
HEAD core/app.py = EVIL; record names Q whose core/app.py = GOOD
--- PR head f98dd2a:
errors: []
notices: []
--- base 6afc545:
errors: ["reviews/9/r.json: STALE — this record reviewed 'a1688d97...', but the current REVIEWABLE head is '92735864...'",
         "a1688d973a64: touches a shared path and has 0 independent review(s) in reviews/9/, needs 1", ...]
```
Walk-level trace:
```
--- PR head script: resolve_reviewable_head -> 0ebee2b (=Q) | order visited: M, X, Q
    diff reviewable-head vs M (non-record): core/app.py
--- base script: resolve_reviewable_head -> 12ab7ac (=M) | order visited: M
    diff reviewable-head vs M (non-record): (none)
```
At the fixed head the gate is fully green on a PR whose reviewable content
(Q) was never diffed against what the merge actually ships (EVIL). The base
code correctly rejects it. Two fixes: walk with `--first-parent`, or when a
merge is judged record-only, continue the walk from its first parent
explicitly. Plausible-but-unreproduced: the same ordering issue can misfire
honestly too (e.g. a cherry-pick on `main` landing between a record-only merge
and the PR branch tip could stale a valid record) — not confirmed.

**F2 (confirmed): one AGREE can now silently outvote real DISAGREEs, self-reviews
and malformed records, contradicting the PR's "nothing weakened" claim.**
`_review_ok` itself is unchanged, but every rejection now goes into a local
list that becomes a non-fatal NOTICE once one valid record exists elsewhere.
```
PR head, REQUIRED_INDEPENDENT_REVIEWS=1, one valid AGREE present, plus:
  3x DISAGREE:      ok=True errors=0 notices=3
  self-review rec:  ok=True errors=0 notices=1
  malformed JSON:   ok=True errors=0 notices=1
  DISAGREE (notices param=None): ok=True errors=0 notices=None
base, same inputs:
  3x DISAGREE:      ok=True errors=3 notices=0
  self-review rec:  ok=True errors=1 notices=0
  malformed JSON:   ok=True errors=1 notices=0
```
No rejected record is ever counted toward the required total (`reviewer_ids.add`
only runs on a valid id), so the count can't be inflated — but today a single
DISAGREE blocks merge, and after this fix three DISAGREEs from distinct
reviewers no longer block anything once one AGREE exists. `reviews/README.md`
states only `"AGREE"` satisfies the gate; this PR changes that policy without
saying so. When the caller passes no `notices` list at all, a rejected
record's reason is dropped with no error and no notice — "checked, found
nothing" and "could not check" become the same shape, though today's only
caller always supplies a list, so CI is unaffected by this specific path now.

**F4 (confirmed): the PR's own proof record doesn't cover its head.**
`proof/54.json`'s `commit` is `a55dbdf4b7399579c7d6e3e31f566cad2a87401e`,
which predates both the defect-2 commit and the actual head. Its recorded
pytest tail is `595 passed`, not 601 — the merge-diff half of the PR is

**F5 (plausible, not reproduced): every merge now feeds the lane-ownership
check too.** `check_lanes` runs its lane-ownership loop over `commit_files(sha)`

main's whole first-parent diff (30 files for two sampled merges), attributed to
the merging agent — so a codex-lane file arriving via a main-merge could fail
a claude branch's lane check. Not reproduced end-to-end on a real branch.

- No `verifiable:false`-style exemption on deterministic output found in this diff; `_commit_parents` uses `check=True` so a git failure raises rather than silently passing.
