### F1 (CONFIRMED). The "every file must be a record file" rule has no test. Invert it and the suite stays green, while a mixed code commit gets past the identity gate.

This PR makes `lwb_check_commit_identity._authors` skip any commit for which `lwb_lanes._is_record_only_commit(sha, pr)` is True. The only thing stopping a commit that touches `reviews/45/` plus real code from being skipped is the "every file" loop. Replacing it with an "any file" test in a scratch copy:
```
$ sed -i 's|        if not (posix.startswith(reviews_prefix) or posix == proof_file):|        if not any(x.replace(chr(92), "/").startswith(reviews_prefix) or x.replace(chr(92), "/") == proof_file for x in files):|' scripts/lwb_lanes.py
$ python -m pytest -q | tail -1

```
The same broken module, run against a scratch repo commit by `Mallory <m@evil.example>` touching `reviews/45/r.json` and `core/evil.py`:
```
mutated record_only(mixed, 45): True
mutated identity findings: []
```
- **Failure scenario:** a future refactor that makes this mistake lets any identity land code in a PR by bundling one `reviews/<pr>/` file with it. It would also move the reviewable head back past that code. CI would stay green.
- **Pre-existing part:** `main`'s tests did not pin this either. The difference is that on `main` the function only fed the freshness check. This PR connects it to the identity gate, so the missing test now matters more.
- **The unmodified code is correct.** Against `073034f`, the same mixed commit gives `False` and `['Mallory <m@evil.example>']` (probe output under F4).

### F4 (CONFIRMED, relaxation not disclosed). The identity exemption is new relative to `main`, CI behaviour does change, and it covers more than the stated need.

- On `main`, `lwb_check_commit_identity.py` has no exemption at all. `git show e5f29bf:scripts/lwb_check_commit_identity.py | grep -n "record\|reviews"` finds nothing.
- The PR body calls B3 a narrowing of something that "used to treat ANY commit … as exempt from identity/freshness checks". Compared with `main`, the identity half is a new relaxation; the broad identity exemption only ever existed on #40.
- "`--pr-number 0` / omitted means … the default behavior is unchanged" is true for the command line. It is not true for CI: `ci.yml` now passes `--pr-number ${{ github.event.pull_request.number }}`, so CI's behaviour changes.
- Probe on unmodified code:
  ```
  identity ['reviews/45/r.json'] pr45 -> []  pr0 -> ['Mallory <m@evil.example>']
  identity ['proof/45.json'] pr45 -> []  pr0 -> ['Mallory <m@evil.example>']
  identity ['reviews/45/r.json', 'core/z.py'] pr45 -> ['Mallory <m@evil.example>']  pr0 -> ['Mallory <m@evil.example>']
  ```
- The stated reason is that a reviewer files a `reviews/<pr>/` record under their own identity. The exemption also covers `proof/<pr>.json`, which is the author's completion claim, not a reviewer record. So any git identity can now write a PR's proof record without failing the identity gate. That is wider than the stated need, and nothing in the PR says why proof records need it.
- This is a policy question under owner directive 10. It should be stated as a relaxation of `main`, not as a narrowing.

### F5 (CONFIRMED, weakens the self-review check). A product name is now accepted as the session token, and two ids with the same product-name token no longer register as a self-review.

```
_parse_identity('worker-claude-buildcraft-2026-09-24') -> ('worker-claude', 'buildcraft', '2026-09-24') []
_parse_identity('cto-claude-LWB-2026-09-24')           -> ('cto-claude', 'LWB', '2026-09-24') []
PR  _shared_long_segment('worker-claude-buildcraft-…','cto-claude-buildcraft-…') -> None
BASE (e5f29bf) same pair                                                      -> buildcraft
```
- The format check accepts a word from the new ignore list (`buildcraft`, `leapware`, `lwb`) in the session-token position, and the shared-token check then ignores it. An author and a subagent that both put "buildcraft" in the token slot were flagged on `main` and now pass.
- That is exactly the accidental self-review `reviews/README.md` says this check exists to catch. The PR's own test `test_review_ok_at_cutoff_accepts_ids_sharing_only_the_product_name` treats it as the intended behaviour.
- Suggested fix: reject an ignore-list word as the session token in `_parse_identity`.
- Severity is moderate: the README already admits deliberate evasion is undetectable, so this only affects the accidental case.
