## Summary
The rule-level change works as far as it goes. `repo is None` and `facts_incomplete` now deny under DENY and are unchanged under WARN, and my mutation probes show the suite pins this. But under `deny`, the rule still allows a publish in at least three repo states that git itself cannot read. The collector reports each of them as `branch=None, facts_incomplete=False`, which is the same thing it reports for a detached HEAD. The PR puts that shape out of scope, and its docs justify that with a premise I refuted: "means the adapter read git just fine". The `lwb_lanes.py` gate that the `reviews/51` record satisfies is a shape-only check. It passed a record I fabricated with an invented `reviewer_id`. The branch also conflicts with the current main on `HANDOFF.md`.

## Findings, most severe first

### CONFIRMED 1 (blocking). DENY still permits when git cannot be read: three states land in the detached-HEAD bucket
In `adapters/claude/repo_facts.py`, `_git_dir` returns `None` when `.git` is a worktree pointer to a missing directory, when it has no `gitdir:` prefix, or on an `OSError`. `read_branch_ex` returns `(None, None)` when `.git/HEAD` is missing. None of these sets `facts_incomplete`. The rule then takes the `repo.branch is None and not pr_numbers` branch and returns `None`, even under DENY. Probe (imports the PR-head code, runs the real collector, evaluates a `git push` event with lwb_proof_required=DENY through the engine):
```
A dangling worktree gitdir: repo=RepoFacts(branch=None, proof_ids=(), facts_incomplete=False, facts_incomplete_reason=None) -> permit=True deny=None
B .git dir with no HEAD: repo=RepoFacts(branch=None, proof_ids=(), facts_incomplete=False, facts_incomplete_reason=None) -> permit=True deny=None
C .git file garbage: repo=RepoFacts(branch=None, proof_ids=(), facts_incomplete=False, facts_incomplete_reason=None) -> permit=True deny=None
D control: healthy repo, no proof: repo=RepoFacts(branch='feature-x', ...) -> permit=False deny="publishing command with no proof record for 'feature-x': 0 record(s) found under proof/ ..."
```
Git itself treats states A and B as unreadable:
```
fatal: not a git repository: /nonexistent/wt
fatal: not a git repository (or any of the parent directories): .git
```
`docs/rules/lwb-proof-required.md:180-183` says "`RepoFacts(branch=None, facts_incomplete=False)` means the adapter read git just fine … the rule CAN read git here". The rule docstring and the test `test_detached_head_with_no_pr_number_is_silent_even_under_deny` rest on the same premise. The probe refutes it. So "could not check" and "checked, no identifier" still look identical in deny mode, which is the exact defect this PR claims to close. State A is realistic here: the collector's own docstring says this repo works in worktrees under `.worktrees/`, and a pruned or moved worktree produces a dangling pointer. The PR narrows the gap. It does not close it.
