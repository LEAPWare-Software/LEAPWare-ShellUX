## Findings, most severe first

### CONFIRMED — F1 (blocker, defect shape b): a failed PR lookup and "no PRs found" produce the same output, so the job stays green either way

```
$ PATH=$B/gh-fail:$PATH GITHUB_EVENT_NAME=schedule python3 scripts/cloud/auto_queue.py --find-prs
exit=0
stdout: prs=
stderr: NOTICE: ... exited 1: HTTP 403: Resource not accessible by integration
        NOTICE: could not resolve pull requests for this event

$ PATH=$B/gh-empty:$PATH GITHUB_EVENT_NAME=schedule python3 scripts/cloud/auto_queue.py --find-prs
exit=0
stdout: prs=          # identical
```
`prs=` makes every downstream step skip (`if: steps.find.outputs.prs != ''`), so the run ends green in both cases. The only difference is plain stderr text — not a `::warning::`/`::error::` annotation — so nothing surfaces on the Actions run summary. A persistently failing lookup (revoked token scope, an API shape change) therefore produces a green 15-minute sweep forever, with nothing ever enqueued — silently. This directly contradicts the PR's own docstring for `resolve_pr_numbers` ("callers must treat [None] as 'could not determine' and NOT as 'no PRs concerned'") and the workflow's own adjacent comment ("a path that cannot work must not report the same success as one that does"). This is exactly this PR's own defect-shape (b): "I checked and found nothing" and "I could not check" share a representation.

### CONFIRMED — F2 (blocker): N3's own test passes on a mutation that disables the schedule sweep and manual dispatch, i.e. the self-heal that F1 depends on

| Mutation to the job-level `if:` | `test_auto_queue_job_skips_non_success_workflow_run_conclusions` and full suite |
|---|---|
| delete the `if:` entirely | caught (fails) |
| gate **every** event on `github.event.workflow_run.conclusion == 'success'` | **not caught** — 31 passed |

On `schedule` and `workflow_dispatch`, `github.event.workflow_run.conclusion` is empty, so gating every trigger on it turns off the 15-minute sweep and manual dispatch too — silently, since the job simply doesn't run. The workflow's own comment states "non-`workflow_run` triggers ... must not be gated by it," but no test enforces that; the N3 test only checks the `workflow_run`+non-success case, and its own helper (`gates_conclusion()`) accepts any expression that merely mentions `workflow_run`, `conclusion` and `success` as substrings.

### CONFIRMED — F3 (blocker): N1's "actually invokes the script" test passes even when the script's output never reaches `$GITHUB_OUTPUT`
