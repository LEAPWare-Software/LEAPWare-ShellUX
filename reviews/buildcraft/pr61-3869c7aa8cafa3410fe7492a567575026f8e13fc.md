   `auto-queue.yml` triggers only on `check_suite: [completed]` and

   events this workflow never uses. `checkout@v6`'s credential-file change
   applies to the built-in `github.token` (`contents: read,
   pull-requests: write`) used by the checkout step itself, not to the
   privileged `AUTO_TOKEN_QUEUE` PAT, which is only injected as `GH_TOKEN`

   exposure of the sensitive credential is unchanged by this bump.

4. **Consistency (CONFIRMED).** `auto-queue.yml` was the last workflow in
   the repo still on `checkout@v4`; `ci.yml`, `handoff.yml` and
   `release.yml` are already on `@v7`, and that same v7
   (SHA `3d3c42e5...`) ran green across three OSes in this PR's own CI.

5. **No action in the repository is pinned by commit SHA (CONFIRMED by

   across `.github/workflows/*.yml` is a floating tag. `auto-queue.yml`

   action release could alter the checked-out `scripts/cloud/auto_queue.py`
   that later step then runs with that PAT. This is the one workflow in the
   repo where SHA-pinning matters most and is a pre-existing gap worth its
   own follow-up across all four workflow files, not specific to this PR.

## The real defect this surfaces

Same as PR #60's review: `lwb-proof-pr` requires a `proof/<N>.json` record
that Dependabot cannot author, and `lwb-env-leak` requires
`LWB_PRIVATE_NEEDLES`, a secret that Dependabot-triggered `pull_request`
runs do not receive. As configured today, no Dependabot PR touching a
required-check path can pass this repository's own merge-queue readiness
gate ("every required check is green"), regardless of how safe the
underlying bump is. That is a policy/tooling gap for the repository owner
to resolve, not something a review of an individual dependency-bump PR can
fix.
