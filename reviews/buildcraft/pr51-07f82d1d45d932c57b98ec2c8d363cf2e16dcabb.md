## Findings, most important first

1. **CONFIRMED, real, but correctly non-blocking for merging with shipped defaults: arming `deny` denies every Codex publish, unconditionally.** `adapters/codex/hook_io.py` never populates `repo=` on the `Event` it builds, so `event.repo` is always `None` under Codex. Reproduced by running the shipped Codex hook end-to-end inside a real git repo: under a `deny` policy it returns `"permissionDecision": "deny"` regardless of what proof exists; under `warn` (the shipped default in `core/policy/default.json` and both vendored copies) it stays `allow`. This is disclosed in `docs/rules/lwb-proof-required.md`'s "Known gap: Codex" section, but no test covers it — it should be treated as a blocking known-issue before anyone recommends arming `deny`, not left as a doc footnote only.
2. **CONFIRMED, pre-existing, not introduced by this PR: `RuleMode` is compared with `is` in three places this PR adds (`lwb_proof_required.py:379,411`), following an existing pattern already on `origin/main` (`engine.py:69,97,100`).** A `RuleConfig` built with a plain `"deny"` string (rather than `RuleMode.DENY`) silently drops findings on **both** main and this head — reproduced directly. Not exploitable from any production code path: the only constructor, `load_policy_dict`, always coerces through `RuleMode.coerce`. Correctly not this PR's problem to fix, though using `==` in the new code would have cost nothing and avoided extending the pattern.
3. **CONFIRMED, but Reviewer B's specific finding is stale at this head, not wrong when made.** `proof/39.json` records a digest for `lwb_handoff.py --check`'s output that embeds HANDOFF.md's byte count. At this PR's head the re-executed digest doesn't match the recorded one — but neither does `origin/main`'s (confirmed: main's HANDOFF.md is already a different byte count than when `proof/39.json` was recorded, because #50 changed it independently of this PR). The real underlying defect: `proof/39.json` marks this check `verifiable: true` against output that is not stable across ordinary landings — that record can never reliably re-execute clean, regardless of which PR lands next. Confirmed "report-only in CI": the `--reexecute` step in `ci.yml` runs with `continue-on-error: true` and `if: always()`.
4. **NEW, not raised by either internal review: the shipped Claude hook gives a self-contradicting message when facts are incomplete under `deny`.** `plugins/claude/lwb/bin/lwb_hook.py` is untouched by this diff. Its facts-incomplete warning text still reads "rules that need repository facts (e.g. lwb_proof_required) **may have stayed silent** for this event" and gets appended even to a `deny` decision — reproduced by forcing incomplete facts and running the shipped hook under `deny`: the same output says both "Failing CLOSED under deny" and "may have stayed silent." A nearby comment in the same file ("a broken collector must not block a dispatch") is also no longer accurate once `deny` can be produced from a facts-incomplete state. Not a safety defect — the rule's own docs (line ~151) do correctly describe the new deny behavior — but it fails this project's own "documentation lands in the commit that makes it true" standard for the hook's *own* text, and should be fixed before/alongside arming deny in production, since it would visibly confuse whoever reads that denial.
5. **Minor, unverified interpretively:** the merge commit's regenerated HANDOFF.md "DONE" list (`#7-#39, #50`) includes PR numbers the same document's own prose calls superseded (e.g. #28, #38); the state-claims gate doesn't catch this because it isn't the kind of claim that gate checks.
