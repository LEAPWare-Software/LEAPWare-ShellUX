Verdict: DISAGREE

The script does what its own code says. The report-only wiring is correct, and the PR honestly says it has no token in CI. But two claims about the core design don't hold up when tested. The first is that the gate is "anchored to GitHub's clock". The second is the proof file's statement that its mutation probes show "the suite is not vacuous". Neither is in the PR's list of its own limitations.

## Findings (most severe first)

**1. CONFIRMED: A routine rebase defeats the gate, so "anchored to GitHub's clock" only holds for one of the two timestamps.**
The script compares the issue's `created_at`, which comes from GitHub's clock, against `git log -1 --format=%aI`. That is the git author date, which the author controls. D24, quoted in the script's own docstring, says a git commit timestamp can be forged. Nothing in HONEST SCOPE says the comparison value is forgeable. The docstring picks author date because "commit date ... a rebase can change". But `git rebase --ignore-date` (alias `--reset-author-date`) or `GIT_AUTHOR_DATE` changes the author date too. So "create the issue, then rebase with `--ignore-date`" turns any FAIL into a PASS.
Reproduced in a scratch repo, with a stubbed `_gh_api_json` for an issue created at 2026-09-25T12:00Z:
```
$ GIT_AUTHOR_DATE=2099-01-01T00:00:00+00:00 git commit -qm work ; git log -1 --format='author=%aI committer=%cI'
author=2099-01-01T00:00:00+00:00 committer=2026-09-25T12:55:27+00:00
F forged future author date: PASS: issue #5 created 2026-09-25T12:00:00Z, first commit ef76cd06... authored 2099-01-01T00:00:00+00:00 (26395 days, 12:00:00 later) -- acceptance criteria existed before work started
```
The PASS result has no sanity bound, such as a first commit dated after the PR was opened or after the head commit. An anchor that is actually external would be the first push or the PR's `created_at`, which GitHub records.

**2. CONFIRMED: The two design choices the PR spends the most words defending are not tested. `--first-parent` and author-vs-committer date can both be mutated with the suite staying green.**
```
=== C: drop --first-parent
24 passed in 3.80s
=== D: author date -> committer date   ("--format=%aI" -> "--format=%cI")
24 passed in 3.94s
```
- **`--first-parent`:** the module docstring says plain `base..head` already excludes a forward-merged `origin/main`. So the merge-forward tests (`test_merge_forward_from_base_does_not_change_the_first_commit`, `test_check_acceptance_criteria_uses_the_original_first_commit_through_a_merge`) pass with or without the flag. The one case the flag exists for is an internal side branch with earlier dates, and no test covers it.
- **Author date:** `_commit()` sets `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` to the same value, so no test can tell `%aI` from `%cI`.
- **Proof overclaim:** `proof/68.json` marks both criteria `"met": true`. It also marks this criterion `"met": true`: *"A mutation probe ... confirming the suite is not vacuous"*. That only holds for the two mutations the author picked.

**3. CONFIRMED: The fix for "git %aI version drift" in commit 8a577b0 made the assertion circular rather than fixing it.**
`assert author_date == m._commit_author_date(repo, first_sha)` compares the function's output with a second call to the same function. `assert actual_first_author_date in result.message` has the same problem. Neither assertion checks the date value any more, which is why mutation D above stays green. A correct fix would parse both values and compare them as datetimes, e.g. `_parse_iso8601(author_date) == datetime(2026,9,25,9,0,tzinfo=utc)`. The script's own `_parse_iso8601` does handle both `Z` and `+00:00`, so the script itself is fine; the test lost its power. Reviewer had only local git 2.43.0, so did not confirm that git 2.55 prints `Z`.

**4. PLAUSIBLE, low: `${{ github.event.pull_request.head.ref }}` is placed unquoted in `run:`. This is the first `head.ref` interpolation in any workflow in this repo.**
```
$ grep -n "head.ref\|head_ref\|pull_request_target" .github/workflows/*.yml
.github/workflows/ci.yml:195:          --branch ${{ github.event.pull_request.head.ref }}
```
GitHub's hardening guide names `head_ref` as a script-injection vector, and git ref names allow `;`, `$`, `|` and `&`. The trigger is `pull_request`, not `pull_request_target`, so a fork gets no secrets from this. A branch name containing `;` would still break the invocation or run extra commands. The fix is `env: HEAD_REF: ...` with `"$HEAD_REF"`. Not reproduced.

**5. CONFIRMED, medium: Issue-link parsing gets both negative mentions and legitimate syntax wrong.**
```
H regex: {'This does not close #5': 5, 'Closes owner/repo#5': None, 'Closes: #5': None, 'Fixes https://github.com/o/r/issues/5': None, 'closed #5 was a dup, see #9': 5}
```
- **False matches:** negations and past-tense mentions ("does not close #5", "closed #5 was a dup") count as links.
- **Missed links:** GitHub supports `owner/repo#N` and full issue URLs, and these return no link, which becomes NO_ISSUE_REFERENCE and exits 1. The docstring calls the regex "GitHub's standard closing-keyword syntax".
- **Any issue number passes:** `issues/{n}` also returns PRs. Any number that already exists, such as `Fixes #1`, always gives PASS. HONEST SCOPE does cover "right issue" as a human's call, so this part is only partly undisclosed.

**6. PLAUSIBLE, design: A branch-name exemption applies to every future PR that reuses that branch name.**
`_find_exemption` matches `branch` exactly and the list is append-only, so an entry for a common name like `fix-ci` stays active for later PRs. The file is also read from the PR's own checkout, so a PR can exempt itself and get EXEMPT on its own CI run before anyone reviews the entry. Neither point is disclosed. Low impact while the gate is report-only.

**7. CONFIRMED, minor: "Exemption is checked before the commit range" is only partly covered by tests.**
The behaviour holds (`E exempt + bad base: EXEMPT: ... (pr=1): r`). Moving the exemption block to after range resolution turned 1 test red, `test_branch_in_exempt_file_is_exempt`. It failed because that test passes `pr_number=None`, so the no-PR CONFIG_ERROR check fired first. No test covers "PR exempt, range broken, result EXEMPT".

**Claims that did hold:**
- **Mutation A** (`<=` to `<`): exactly 1 test went red, `test_issue_created_exactly_at_first_commit_is_pass`.
- **Mutation B** (exemption matching disabled): exactly 2 went red, `test_pr_in_exempt_file_is_exempt_even_with_no_issue_reference` and `test_branch_in_exempt_file_is_exempt`.
- **Exit-code map:** PASS/EXEMPT exit 0, FAIL/NO_ISSUE_REFERENCE exit 1, UNVERIFIABLE 2, NO_RANGE 3, CONFIG_ERROR 4, all matching the claim.
- **Error handling:** no exception handler turns a failure into PASS or EXEMPT. Every `gh` error and timestamp parse error becomes UNVERIFIABLE.
- **CI step:** has `continue-on-error: true` and `if: always() && github.event_name == 'pull_request'`, sets no token, and passes `head.sha`, which avoids the synthetic merge ref.
- **"Unverifiable in CI" admission:** honest, and acceptable for a report-only gate. But together with finding 1, even a working token would give a PASS that can be forged.
