## Summary

The plumbing checks out — exit-code mapping, `--first-parent` first-commit
resolution, exemption-checked-before-`gh`, report-only `continue-on-error`
wiring, and the 636-test full-suite count all reproduce exactly as the PR
claims. But the gate this PR ships does not do what D24 asks. Two
independently reproduced defects each let a PR pass acceptance-criteria
review while genuinely failing it, and one of the two is exactly the
failure mode the PR's own docstring quotes D24 as warning against — a
forgeable timestamp — just on the other side of the comparison than the
one D24 anchors. A third defect produces false FAILs on legitimately
worded closing references. This is a DISAGREE on the gate's fitness for
purpose, not on the code quality of the plumbing around it.

## Findings

### Confirmed, most severe — an arbitrary pull request satisfies "the issue"

`GET /repos/{o}/{r}/issues/{n}` also returns pull requests, and the script
never checks the response's `pull_request` key. Any `Fixes #<n>` naming an
older *PR* — not an issue — is accepted as a valid acceptance-criteria
reference, so a PR can point at another PR opened before its own work
started and PASS regardless of when its actual acceptance criteria were
written. Reproduced end to end against this repo's real PRs #1 and #60
(both genuinely PRs, confirmed via the `pull_request` key), with `gh`
replaced by a `curl`-backed wrapper hitting the live API, PR body
`Fixes #1`, and a first commit made today:

```
PASS: issue #1 created 2026-09-17T20:53:35Z, first commit <sha> authored
2026-09-25T13:57:24+00:00 (7 days, 17:03:49 later) -- acceptance criteria
existed before work started
exit=0
```

The HONEST SCOPE section in the module docstring says the issue's *text*
is never read; it says nothing about the referenced item's *type* never
being checked. This is not a documented limitation — it's a silent hole.

### Confirmed, most severe — the non-GitHub side of the comparison is exactly the forgeable timestamp D24 warns about

The module docstring quotes D24 to justify anchoring on GitHub's clock: a
raw git commit timestamp "can be forged." The script then compares
GitHub's (trustworthy) issue-creation time against the first commit's
*author* date — which is that same forgeable timestamp, just used as the
other operand. No check exists that the author date is not after the
committer date, or not in the future. Two independent reproductions:

```
GIT_AUTHOR_DATE=2030-01-01T00:00:00Z git commit --allow-empty -m "..."
-> PASS: issue #3 created 2026-09-25T12:00:00Z, first commit <sha>
   authored 2030-01-01T00:00:00+00:00 (1193 days, 12:00:00 later) ... exit=0
```

and, without fabricating anything at all, an ordinary `git rebase
--ignore-date` — a command contributors run routinely, not an attack —
resets every author date to now and turns a genuine FAIL into a PASS. A
gate whose stated purpose is to defeat a forgeable timestamp, defeated
by that same class of timestamp on its other input, is not a smaller
version of D24; it's a gate that hasn't closed the gap D24 opened.

### Confirmed — the reviewer's own mutation-probe count is stale, not just the PR body's

Disabling `_find_exemption` (returning `None` unconditionally) turns
**3** tests red, not the 2 the PR body claims:

```
_find_exemption -> None:  3 failed, 24 passed
  test_pr_in_exempt_file_is_exempt_even_with_no_issue_reference
  test_branch_in_exempt_file_is_exempt
  test_exempt_entry_with_both_pr_and_branch_set_is_an_or_not_an_and
```

`git log -S` confirms the third test was added in this very head commit
(the F1–F5 fix-up), so the PR's probe number was not re-run after its own
last commit. The timestamp-flip probe (`<=` to `<`) does reproduce exactly
as claimed (1 failed: `test_issue_created_exactly_at_first_commit_is_pass`).
This is a small miss on its own, but it's exactly what CLAUDE.md rule 2
("evidence, not assertion") and this PR's own "measured, not claimed"
section promise won't happen.

### Confirmed — several documented rules have no test that would catch their removal

Each mutation below left all 27 tests in `test_lwb_check_acceptance_criteria.py`
green:
- `pr: true` accepted where an integer is required (bool-as-int check removed)
- `branch: ""` or `branch: 5` accepted (branch type check removed)
- top-level `acceptance_exempt.json` not being an array accepted
- an exemption entry that is not an object accepted
- a missing `created_at` on the fetched issue silently accepted
- the "timezone required" check on parsed timestamps removed
- the empty-range guard removed (a head that is an ancestor of base now
  raises `IndexError` instead of resolving to `NO_RANGE`)

The module docstring promises `CONFIG_ERROR` for malformed exemption
entries and malformed timestamps; none of those promises is backed by an
assertion that would fail if the check were deleted.

### Confirmed — valid GitHub closing syntaxes are missed; a code-fence match wins over a real reference

```
'Fixes: #3'                                    -> None (missed; colon form)
'Fixes LEAPWare-Software/LEAPWare-BuildCraft#3' -> None (missed; owner/repo#n form)
'Fixes https://github.com/.../issues/3'         -> None (missed; full-URL form)
'```\nfixes #7\n```\nCloses #3'                 -> 7   (fenced-code text wins over the real reference)
'Not closing #3; see fixes #9 later'            -> 9   (arguably correct, but shows the regex has no code-fence awareness either way)
```

These are false FAILs / NO_ISSUE_REFERENCEs on legitimately closed PRs,
which is the opposite failure direction from the two most-severe findings
above but still real: once this gate is armed (a stated near-term
follow-up), a contributor who writes `Fixes: #123` gets blocked for no
reason. Whether GitHub itself recognizes the colon and full-URL forms as
closing keywords is PLAUSIBLE from memory, not independently checked here.

### Confirmed — "exemption checked before the commit range" is untested

Reordering `resolve_first_commit` ahead of `_find_exemption` in the
script left all 27 tests passing. Only "exemption checked before `gh`" is
covered by a test; "exemption checked before the commit-range walk" (the
other half of the PR's own claim) is not.

## What holds

- Exit-code mapping: 5 codes (0–4) behind 7 named outcomes, matching the
  script's own docstring ("five", not the "six" this review's brief
  expected — the PR body itself was not accessible to this review to
  confirm which number it uses).
- `--first-parent` first-commit resolution: independently rebuilt with a
  pinned-date side-branch merge; plain `git log --reverse` returns the
  side commit, `--first-parent` returns the correct mainline commit.
  Removing `--first-parent` turns exactly 1 test red.
- Exemption match is genuinely checked before any `gh` call: every exempt
  test stubs `gh` to raise if invoked, and none do.
- `reason: ""`, whitespace-only, and missing `reason` are all rejected
  with a test.
- No `GH_TOKEN`/`GITHUB_TOKEN` anywhere in `ci.yml` outside comments —
  the PR's stated pre-existing gap (this step will report UNVERIFIABLE on
  every real run until that's fixed elsewhere) is real and not made worse:
  the UNVERIFIABLE message surfaces `gh`'s own stderr verbatim, not a
  falsely specific reason.
- `continue-on-error: true` and `if: always() && github.event_name ==
  'pull_request'` on the new step: confirmed report-only, cannot block a
  merge. The branch name flows through `env:`, not string-interpolated
  into the shell command — safe from injection.
- A 404 (bad issue reference) and an auth/network failure both exit 2
  under the same UNVERIFIABLE tag; only free-text stderr differs, nothing
  machine-readable separates them. Disclosed as deliberate by the PR, but
  worth naming precisely since D1 above means a 404 on a *good-faith*
  typo and D1's exploit of a *PR* reference share no distinguishing
  signal either.
- Full suite: 636 passed (needs PyYAML installed locally — without it,
  633 passed / 3 skipped in `test_workflows_parse.py`).
