## Findings BuildCraft's own internal review missed (new here)

1. **Undercharged, should be a blocking doc/code issue: the per-branch deletion allowlist can be widened by a single command.** The rule's own docstring and doc page claim `verified_landed_branches` scopes authorization "to one branch at a time rather than blanket." Reproduced false:
   ```
   opts={'verified_landed_branches': ['landed']}
   'git push origin --delete unlanded landed'                              -> SILENT (target='landed')
   'git push origin :landed :unlanded'                                     -> SILENT
   'git push origin --delete landed && git push origin --delete unlanded'  -> SILENT
   ```
   Cause: only one ref is extracted per segment, and only the first matching segment is checked — the same root defect the sibling PR #52 review found independently (segment-order dependence), but this is the *single-segment* multi-ref variant, not covered by that finding. No test covers multiple refs. This should be named as a known blind spot in the docs (currently overclaimed as scoped) before merge, and fixed in code before the rule can be armed to deny.
2. **False positives** (the docstring claims deliberate under-matching, but these warn): `git rebase --abort`, `git rebase --continue`, `git filter-repo --analyze`, `gh api -X POST repos/o/r/issues -f title=update-rulesets-doc`, `gh api -X POST repos/o/rulesets-demo/issues` (the last two: `_SETTINGS_PATH_MARKERS` substring-matches any non-flag token, including field *values*, not just the path). At `warn` this is only noise; once armed, `git rebase --abort`/`--continue` false-DENY would block recovering from a rebase — the one defect class here that produces a false DENY rather than a missed one.
3. **Undocumented blind spots** beyond the docstring's "accepted and named" list: `gh api repos/o/r/rulesets -f name=x` (POST is implied by passing fields; the docstring's claim that GET-default `gh api` calls are never mutating is wrong), `gh api -XPATCH repos/o/r`, `git push origin +main` (a `+`-refspec force-push), `git rebase -n` (see B above).
4. **Possible mismatch with decision D19** (not fully tested, interpretive): `gh pr merge 5 --admin --squash` is SILENT because merges are unconditionally carved out, but D19 authorizes only "merging a PR whose gates and independent review passed" — `--admin` bypasses branch protection.
5. **The commit-identity check only reads the commit *author*, not the *committer*.** `8f3bddc`'s committer field is `Claude <noreply@anthropic.com>` (its author is correctly `LEAPWare`); `ad92d5e`'s committer was `LEAPWare`. Directive 10 is worded in terms of author, so this doesn't break the check as written — but it means "byte-for-byte" is true of file contents, not of the commit object itself, and "verified commit identity throughout" never actually looks at the committer field. This is the standing "field read while a sibling that changes its meaning is silently ignored" pattern.
6. **Design point, not a bug:** the rule stays silent under `facts_incomplete` despite never reading any repo fact — the same "could not check reads as checked, nothing found" pattern flagged in the PR #52 review, carried forward unchanged here.
